# flan — DESIGN

> Статус: черновик v2 дизайна. Описывает, **каким flan должен стать**, а не каким он является сейчас.
> Текущее состояние кода разобрано в разделе [2](#2-что-есть-сейчас-и-что-с-этим-не-так), план перехода — в [12](#12-план-перехода).

## 1. Зачем flan и чем он не является

**flan** — пакетный менеджер для Windows, который ставит **портативные** программы (zip-архив или одиночный `.exe`) в каталог пользователя, без прав администратора.

### Цели (в порядке приоритета)

1. **Лёгкость.** Один `flan.exe` без зависимостей (ни .NET, ни PowerShell, ни VC++ Redistributable). Из системы он берёт только то, что входит в саму Windows, в том числе Universal CRT (`ucrtbase.dll`): в Windows 10/11 это часть ОС, в 7/8.1 — обновление KB2999226 (см. [10](#10-сборка-и-размер)). Целевой размер — **≤ 200 КБ** (x64 Release), желательно ≤ 150 КБ. Самообновление должно скачиваться за секунды даже на медленном канале.
2. **Медленный и нестабильный интернет.** Ничего не качать повторно: условные запросы, докачка, кэш по хэшу, сжатый индекс.
3. **Слабое железо** (Celeron, HDD, 4 ГБ RAM). Один проход по файлу, никаких дочерних процессов на горячем пути, без загрузки всего в память там, где этого можно избежать.
4. **Безопасность по построению.** Всё, что пришло из сети, — недоверенные данные. Установка никогда не запускает код пакета.
5. **Простота.** Код должен помещаться в голове одного человека.

### Не-цели (сознательно)

| Не делаем | Почему |
|---|---|
| MSI / NSIS / Inno-установщики | Это запуск чужого кода с непредсказуемыми последствиями. flan ставит только то, что можно распаковать. |
| Права администратора, установка «для всех пользователей», службы | Противоречит модели «всё в профиле пользователя» (см. ниже). |
| Разрешение зависимостей | Портативные программы почти никогда их не требуют. Поле зарезервировано на будущее (см. [13](#13-открытые-вопросы)). |
| GUI | Только консоль. |
| Скрипты установки в манифестах | Причина та же, что у установщиков. |
| Изменение PATH и переменных среды пакетами | Единственная запись flan в PATH — `.flan\bin`; команды пакетов попадают туда через прослойки. Сознательный отказ от `env_add_path` в духе Scoop: PATH не разрастается с каждым пакетом, а удаление пакета не оставляет в нём хвостов. |

### Без прав администратора

flan **никогда** не требует прав администратора и не вызывает окно UAC. Всё, что он создаёт, находится в одной папке внутри домашнего каталога пользователя — `$HOME\.flan` (`%USERPROFILE%\.flan`), а этой папкой пользователь и так владеет полностью.

Следствия для дизайна:

| Куда пишет flan | Куда **не** пишет |
|---|---|
| `%USERPROFILE%\.flan\` — программы, прослойки, кэш, состояние | `C:\Program Files`, `C:\Windows`, корень диска |
| `HKCU\Environment\Path` — PATH текущего пользователя | `HKLM` — системный PATH и любые машинные настройки |
| — | службы, планировщик задач, драйверы, ассоциации файлов |

- В `flan.exe` и `shim.exe` вшит явный манифест (свой `.manifest`-файл, а не умолчание Visual Studio, плюс `supportedOS` для Windows 7–11) с `requestedExecutionLevel level="asInvoker"`. Без него Windows может сама запросить повышение прав у 32-битного `.exe`, в имени которого есть `install`, `setup` или `update` (так работает эвристика Installer Detection).
- Если flan всё же запустили от имени администратора, он выводит предупреждение: в этом нет смысла, а файлы, созданные повышенным процессом, могут потом мешать обычному.
- Отсюда же портативность: папку можно перенести через `FLAN_HOME` (например, на флешку), а удаление flan целиком — это `flan setup --remove` и удаление одной папки.
- Отсюда же граница возможностей: всё, что требует прав администратора (установщики MSI, службы, драйверы), flan не ставит по определению.

### Поддерживаемые платформы

- **Официально:** Windows 10 / 11, x64 и x86.
- **Без гарантий:** Windows 7 SP1 / 8.1, только с обновлением KB2999226 (Universal CRT, см. [10](#10-сборка-и-размер)); без него `flan.exe` не запустится. Мы не тестируем их, но и не используем API, которые их ломают без нужды (см. TLS 1.2 в [7.2](#72-сеть)).
- ARM64 — зарезервирован в формате, не собирается.

## 2. Что есть сейчас и что с этим не так

Исходная точка — локальная ветка с исправлениями уязвимостей (ещё не закоммичена). Эти исправления правильные и переносятся в новый дизайн: белый список имён (`validate.hpp`), проверка границ при разборе базы, загрузка только по HTTPS с лимитом размера и записью через `.part`, запуск `tar.exe` по явному пути без оболочки.

Ниже — проблемы, которые точечными правками не решаются, потому что они в самой архитектуре.

| # | Проблема | Следствие |
|---|---|---|
| A1 | **Два источника правды**: `core.flan` (имя → id) и `meta/<id>.json` (всё остальное) поддерживаются вручную | id разъезжаются (`ripgrep` → id 1, файл `meta/101.json` → 404). `flan install` сейчас не работает ни для одного пакета. |
| A2 | Установка = **2 сетевых запроса** (метаданные + архив) | Лишний round-trip на медленном канале; метаданные не покрыты ничем, кроме HTTPS. |
| A3 | Индекс ничем не подписан | Кто контролирует репозиторий (или токен GitHub), тот контролирует, что запустится у пользователя. SHA-256 архива защищает только от порчи в пути, но не от подмены самих метаданных. |
| A4 | `hash_v` и `timestamp` в формате есть, но не используются; комментарии со смещениями в `CoreHeader` не совпадают с реальной раскладкой (magic на 8, а не на 0, и т.д.) | Формат живёт без спецификации. |
| A5 | `nlohmann/json` (950 КБ заголовка), `<iostream>`, `<filesystem>` в клиенте | x64 Release весит ~430 КБ, Win32 ~365 КБ — в 2–3 раза больше цели. |
| A6 | Все пути через ANSI-функции (`SHGetFolderPathA`, `CreateDirectoryA`, `DeleteFileA`) | Ломается на кириллическом имени пользователя; нет поддержки путей длиннее `MAX_PATH`. |
| A7 | Распаковка через `System32\tar.exe` | Нет на Windows до 10 1803; отдельный процесс на каждую установку; нельзя проверить имена внутри архива до записи. (Срезать верхнюю папку архива `tar.exe` умеет — это bsdtar с `--strip-components`, — но только вслепую, не глядя, что внутри.) |
| A8 | `.bat`-прослойки | Вызов `.bat` из другого `.bat` без `call` молча обрывает вызывающий скрипт; Ctrl+C даёт «Завершить выполнение пакетного файла [Y/N]?»; `%` и `^` в аргументах могут перетолковываться; в прослойке зашит абсолютный путь; если `.bat` удалить, пока работает его команда (`uninstall`), `cmd.exe` печатает «The batch file cannot be found.», и код возврата этого запуска становится 1. |
| A9 | Повторный `install` распаковывает поверх существующего каталога | Файлы старой версии смешиваются с новой. Нет обновления как такового. |
| A10 | `installed.json` — один файл, переписывается целиком, без блокировки | Два параллельных `flan` портят реестр; сбой посреди записи теряет все записи. |
| A11 | SHA-256 считается **вторым проходом** после загрузки; оборванная загрузка начинается заново | Двойное чтение с HDD; на плохом канале большой архив может не скачаться никогда. |
| A12 | `bin` добавляется в `PATH` только на словах (в README) | После установки команды не находятся. |
| A13 | Нет `upgrade`, `search`, `info`; `list` показывает доступные пакеты, а не установленные | Непривычная семантика команд. |

## 3. Архитектура в одном абзаце

Автор репозитория пакетов пишет **манифесты** (`packages/<name>.json`). Генератор **`flan-build`** проверяет их, скачивает каждый архив один раз, считает хэши, убеждается, что нужные файлы в архиве есть, и собирает **один подписанный сжатый индекс** `index.flan`. Клиент **`flan`** скачивает индекс (условным запросом — обычно 0 байт), проверяет подпись, а при установке делает **ровно один** сетевой запрос — за самим архивом, — сверяет SHA-256 на лету, распаковывает своим кодом в версионный каталог и создаёт маленькую `.exe`-прослойку.

```
 flan-packages (git)                    машина пользователя
 ┌──────────────────────┐               ┌──────────────────────────────┐
 │ packages/*.json      │               │ flan sync                    │
 │        │             │   HTTPS       │   If-None-Match → 304 / 200  │
 │   flan-build         │──index.flan──▶│   проверка подписи           │
 │   (проверка, хэши,   │               │   защита от отката           │
 │    подпись)          │               │                              │
 │        ▼             │               │ flan install rg              │
 │ index.flan           │               │   поиск в индексе (локально) │
 └──────────────────────┘               │   скачивание архива + SHA-256│
                                        │   распаковка → apps\…\ver\   │
 upstream (GitHub Releases) ──архив────▶│   прослойка bin\rg.exe       │
                                        │   квитанция apps\…\receipt   │
                                        └──────────────────────────────┘
```

Ключевые решения:

- **Один индекс = единственный источник правды** для клиента. Нет `meta/`, нет числовых id. Ключ — имя пакета.
- **Клиент не разбирает JSON.** JSON нужен только людям (манифесты) и генератору.
- **Доверие идёт от ключа подписи**, а не от GitHub. HTTPS — транспорт, не гарантия.

```
flan/
├── flan.sln
├── src/
│   ├── cli/          main.cpp — разбор аргументов, вывод, коды возврата
│   ├── core/         index.cpp, install.cpp, receipt.cpp, shim.cpp, lock.cpp
│   ├── net/          http.cpp (WinHTTP)
│   ├── io/           fs.cpp (только W-функции), zip.cpp, console.cpp
│   └── crypto/       sha256.cpp (потоковый), signature.cpp (ECDSA P-256)
├── include/flan/     format.hpp, validate.hpp, keys.hpp, … (общие с flan-build)
├── shim/             shim.cpp — отдельный проект, без CRT, ~5–10 КБ
├── tools/flan-build/ генератор индекса (C++, может тянуть nlohmann — размер неважен)
├── third_party/      miniz (MIT): tinfl — в клиенте, tdefl — только в flan-build; nlohmann/json.hpp — только для flan-build.

```

`format.hpp`, `validate.hpp` и `zip.cpp` **общие** для клиента и генератора: генератор отвергает всё, что отверг бы клиент, по одному и тому же коду.

Эта раскладка вводится первым шагом этапа 1 — только переносами, без изменения логики.

## 5. Репозиторий пакетов

### 5.1. Раскладка

```
flan-packages/
├── packages/
│   ├── ripgrep.json
│   └── …
├── index.flan        ← генерируется flan-build, руками не править
└── README.md
```

`core.flan` и `meta/` удаляются. Пока пакеты добавляет только автор, `index.flan` коммитится в `main` рядом с манифестами. Когда появятся чужие PR и CI, индекс уедет в отдельную ветку `dist` или в GitHub Releases (см. [13](#13-открытые-вопросы)).

URL индекса в клиенте: `https://raw.githubusercontent.com/muirbil/flan-packages/main/index.flan`. Для отладки и для проверки до публикации переопределяется переменной `FLAN_REPO` (вводится на этапе 1). Это база, к которой дописывается `/index.flan`:

- начинается с `https://` — база URL;
- иначе — путь к локальному каталогу (например, к клону `flan-packages`), и файл копируется вместо скачивания. Скопированный файл проходит **те же шаги приёма**, что и скачанный ([§6.1](#61-конверт-то-что-лежит-на-сервере)): копия во временный `.part`, полная проверка, атомарная замена `state\index.flan`. Прямо в `state\index.flan` он не кладётся никогда.

Подпись при этом всё равно проверяется (с этапа 4).

### 5.2. Манифест

```json
{
  "name": "ripgrep",
  "version": "14.1.1",
  "description": "Recursively search directories for a regex pattern",
  "homepage": "https://github.com/BurntSushi/ripgrep",
  "license": "MIT",
  "bin": ["rg.exe"],
  "arch": {
    "x64": {
      "url": "https://github.com/BurntSushi/ripgrep/releases/download/{version}/ripgrep-{version}-x86_64-pc-windows-msvc.zip",
      "extract_dir": "ripgrep-{version}-x86_64-pc-windows-msvc",
      "sha256": "<заполняет flan-build hash>"
    },
    "x86": {
      "url": "https://github.com/BurntSushi/ripgrep/releases/download/{version}/ripgrep-{version}-i686-pc-windows-msvc.zip",
      "extract_dir": "ripgrep-{version}-i686-pc-windows-msvc",
      "sha256": "<заполняет flan-build hash>"
    }
  }
}
```

| Поле | Обязательное | Правило |
|---|---|---|
| `name` | да | `isSafeName`, только строчные буквы, совпадает с именем файла. Имя из командной строки клиент приводит к нижнему регистру |
| `version` | да | `isSafeName` (становится именем каталога). Строже прежнего `isSafeVersion`: `1.0+build` не пройдёт |
| `description` | нет | ≤ 100 байт, без управляющих символов |
| `homepage`, `license` | нет | только для людей, в индекс не попадают |
| `bin` | да | 1–8 элементов, каждый проходит `normalizeRelativePath` и оканчивается на `.exe` (прослойка запускает цель через `CreateProcessW`, а он не запускает `.cmd`/`.bat`); путь относительно корня приложения (после `extract_dir`). Имена команд (последний сегмент без `.exe`) внутри пакета не повторяются |
| `arch.<a>.url` | да | `https://`, без «плавающих» ссылок вроде `/latest/` — иначе хэш однажды перестанет совпадать |
| `arch.<a>.extract_dir` | нет | подкаталог архива, который становится корнем приложения; проходит `normalizeRelativePath` |
| `arch.<a>.sha256` | да | 64 hex-символа |
| `arch.<a>.kind` | нет | `zip` (по умолчанию) или `exe` — одиночный исполняемый файл, копируется как есть. Для `exe`: в `bin` **ровно один** элемент — имя файла без подкаталогов (например, `"jq.exe"`); скачанный файл ложится в каталог версии под этим именем; `extract_dir` запрещён. Самообновление `flan` (§7.9) — отдельный путь в `bin\`, эти правила его не касаются |

- Неизвестные поля — и на верхнем уровне, и внутри `arch.<a>` — ошибка: почти всегда это опечатка вроде `extractdir`, которая иначе молча потерялась бы.
- Ключи `arch`: `x64`, `x86` и `arm64`. Последний формат резервирует; клиент его пока не выбирает (см. [7.6](#76-транзакция-установки--обновления), шаг 1).

`{version}` подставляется генератором. Обновление пакета = поменять `version` + `flan-build hash`. Больше ничего руками.

### 5.3. Правила приёма пакетов

- Только портативные сборки от первоисточника (предпочтительно GitHub Releases апстрима). flan ссылается на апстрим, а не хранит копии.
- Ссылка указывает на конкретную версию, а не на «последнюю».
- Архив ≤ 512 МБ, распакованный размер ≤ 2 ГБ. Распакованный размер генератор проверяет с этапа 3, своим `zip.cpp`: `tar.exe -tf` размеров не сообщает.
- Имя пакета — имя апстрима в нижнем регистре.
- **Пакет `flan`** — сам flan: `kind = exe`, `bin = flan.exe`, версионные ссылки на выпуски `muirbil/flan`, например `https://github.com/muirbil/flan/releases/download/v0.4.0/flan-x64.exe` и `flan-x86.exe`. Сборка не воспроизводима побайтно, поэтому `flan-build hash` берёт хэш с опубликованного файла, а не с локального. Команда `flan` зарезервирована: никакой другой пакет не может иметь `bin` с именем `flan.exe` — отказ и в `flan-build check`, и при установке.

## 6. Формат индекса (`index.flan`, формат 2)

Все числа little-endian, структуры упакованы (`#pragma pack(1)`), размеры зафиксированы `static_assert`. Файл состоит из **конверта** и **тела**.

### 6.1. Конверт (то, что лежит на сервере)

```cpp
struct Envelope {               // 88 байт
    char     magic[8];          // "FLANIDX\0"
    uint16_t envelope_version;  // = 1
    uint8_t  key_id;            // какой встроенный публичный ключ проверяет подпись; 0 = без подписи
    uint8_t  compression;       // 0 = нет, 1 = raw deflate
    uint32_t payload_size;      // байт тела после конверта (сжатого)
    uint32_t raw_size;          // байт тела после распаковки
    uint32_t reserved;          // = 0
    uint8_t  signature[64];     // ECDSA P-256, r||s
};
// Подпись покрывает SHA-256( первые 24 байта конверта || payload ).
```

- **`key_id = 0` — индекс без подписи**, `signature` — нули. Такие индексы выпускает только генератор этапов 1–3. Клиент этапа 4 и новее отвергает `key_id = 0` **безусловно** — без флагов и переменных окружения, иначе атака «снять подпись» становится тривиальной.
- **`compression = 0` → `payload_size == raw_size`**, иначе индекс отвергается.

Порядок проверки в клиенте — **строго такой**:

1. Размер файла ≤ 8 МБ и `== sizeof(Envelope) + payload_size`.
2. `magic`, `envelope_version`, известный `key_id`, `reserved == 0`.
3. **Подпись** (с этапа 4; до него `key_id = 0` и шаг пропускается). До её проверки ни один байт тела не попадает в распаковщик или парсер.
4. Распаковка с жёстким потолком `raw_size ≤ 32 МБ`; результат обязан быть ровно `raw_size` байт (с этапа 2; до него `compression = 0`).
5. Разбор тела с проверкой всех границ (как в прежнем `loadDatabase`, только в 64-битной арифметике везде).
6. **Защита от отката** (с этапа 4) — по номеру ключа и `generated_at` последнего принятого индекса. Оба числа хранятся в `state\index.state`, а «последнее принятое» — наибольшее из записанного там и из локального `state\index.flan`: удаление одного из файлов счётчик не сбрасывает.
   - `key_id` меньше последнего принятого — отказ: индекс подписан выведенным из употребления ключом. Клиент, хоть раз принявший индекс нового ключа, больше никогда не примет старый — ещё до выхода версии flan без него ([6.3](#63-подпись-и-ключи)).
   - `key_id` больше — индекс принимается без сравнения `generated_at`, дальше счётчик идёт от него. Так смена ключа снимает «заморозку»: украденным ключом можно подписать индекс с `generated_at` из далёкого будущего, и все честные индексы после него выглядели бы откатом. Подделать подпись нового ключа нельзя, поэтому сброс безопасен. Ограничения «не позже, чем сейчас + сутки» нет: на машине с севшей батарейкой часов честный индекс выглядел бы пришедшим из будущего.
   - Тот же `key_id` — `generated_at` ≥ последнего принятого, иначе отказ («похоже на откат индекса»). Равенство допустимо: это тот же индекс, скачанный повторно.
7. Атомарная замена локального `index.flan` (запись в `.part` → `MoveFileExW(…, MOVEFILE_REPLACE_EXISTING)`).

Локальный `state\index.flan` при каждой загрузке (`list`, `install`, `upgrade`) заново проходит шаги 1–5, **включая подпись** — это одна проверка ECDSA. Испорченный файл — код 4, как и при `sync`.

### 6.2. Тело

```cpp
struct IndexHeader {            // 32 байта
    char     magic[8];          // "FLANBODY"
    uint16_t format;            // = 2
    uint16_t entry_size;        // = sizeof(IndexEntry); позволяет добавлять поля в конец
    uint32_t entry_count;
    uint64_t generated_at;      // unix-время сборки; монотонно растёт
    uint32_t strings_offset;    // от начала тела
    uint32_t strings_size;
};

struct StrRef { uint32_t off; uint32_t len; };   // off — от начала пула строк (strings_offset); без '\0'

struct IndexEntry {             // 88 байт
    StrRef   name;
    StrRef   version;
    StrRef   url;
    StrRef   extract_dir;       // len = 0 → корень архива
    StrRef   bins;              // "rg.exe" или "bin\\a.exe;bin\\b.exe" (';' недопустим в путях — разделитель однозначен)
    StrRef   description;
    uint32_t archive_size;      // точный размер архива в байтах
    uint8_t  arch;              // 1 = x86, 2 = x64, 3 = arm64
    uint8_t  kind;              // 1 = zip, 2 = exe
    uint16_t reserved;
    uint8_t  sha256[32];        // бинарный, не hex
};
```

- Таблица записей начинается сразу за `IndexHeader` (смещение 32 от начала тела), а `strings_offset` не меньше её конца.
- Записи **отсортированы по `(name, arch)`**: имена сравниваются побайтово, при равных именах — по числовому `arch`.
- Пределы, которые клиент проверяет сверх границ: `entry_size` ≤ 4096; длина любой строки ≤ 4096 байт; `archive_size` от 1 байта до 512 МБ; `arch` ∈ {1, 2, 3}; `kind` ∈ {1, 2}; при `kind = 2` (exe) — ровно один `bin` без подкаталогов и пустой `extract_dir`. Поле `reserved` записи не проверяется — его могут занять будущие версии.
- `entry_size` больше известного клиенту `sizeof(IndexEntry)` → клиент читает известную часть каждой записи и пропускает остаток; меньше → индекс отвергается.
- **Когда что проверяется.** При приёме индекса (`sync`) клиент один раз проверяет **все** записи: каждую строку — той же проверкой, что и генератор (`isSafeName`, `normalizeRelativePath`, `isHttpsUrl`…), и порядок сортировки. Индекс подписан, но двойная проверка дешёвая и защищает от ошибки в самом генераторе. Остальные команды работают с уже принятым локальным индексом: границы проверяются всегда, строки — только у найденной записи, поиск двоичный.
- `archive_size` даёт: прогресс без `Content-Length`, проверку свободного места до загрузки, сообщение «будет скачано 4.2 МБ» перед установкой, раннюю остановку при превышении.
- Отдельный «хэш версии» (`hash_v`) больше не нужен: **идентичность сборки — её `sha256`**. Обновление доступно, если `sha256` в индексе ≠ `sha256` в квитанции. Сравнивать строки версий (`1.10` vs `1.9`, `-beta`) не нужно вовсе; репозиторий — источник правды, в том числе при откате версии пакета автором.

**Оценка размера:** ~88 байт записи + ~230 байт строк; после deflate (URL-ы хорошо сжимаются) ≈ 100–130 байт на пакет. 1000 пакетов ≈ 120 КБ — это ~15 с на 64 кбит/с, и только когда индекс действительно изменился.

### 6.3. Подпись и ключи

- Алгоритм — **ECDSA P-256 + SHA-256 через CNG (`BCryptVerifySignature`)** (решено на этапе 4, [13](#13-открытые-вопросы), вопрос 2). Он есть в Windows начиная с Vista, поэтому проверка подписи добавляет к `flan.exe` десятки строк кода и ноль байт сторонних библиотек. Ed25519 в CNG нет — его пришлось бы встраивать (например, Monocypher). Подпись CNG — сразу `r||s` по 32 байта, как в конверте.
- **Номер ключа.** `key_id` в конверте — номер ключа, а не номер слота. Номера только растут: 1, 2, 3…; 0 — «без подписи». Открытые ключи (`X||Y`, 64 байта) вкомпилированы в `include/flan/keys.hpp`, до двух штук: **рабочий** и **запасной**. Запасной вкомпилирован во все клиенты с первого дня, а его приватная часть лежит только в резервных копиях.
- **Тестовые ключи** 240 и 241 знают только Debug-сборки клиента, `flan-build` и тестов, как `FLAN_DEBUG_ENV_HIVE`. Их приватные части лежат в `tests\keys\` открыто, под известной фразой: на них проверяется всё, включая смену ключа, а настоящим ключом не подписывается ни один тестовый индекс. Release-сборка тестовых ключей не знает, и `static_assert` это проверяет.

**Где лежит приватный ключ.**

- **Рабочая копия** — `%LOCALAPPDATA%\flan-build\key-<номер>.flankey`: заголовок `FLANKEY1` с номером ключа и открытой частью, затем блоб `CryptProtectData` (DPAPI, текущий пользователь) с приватной частью. `%LOCALAPPDATA%` не синхронизируется ни перемещаемым профилем, ни OneDrive.
  - DPAPI защищает от **утечки файла**: ключ не расшифровать на другой машине или под другой учёткой, из копии профиля, бэкапа диска или случайного коммита.
  - От программы, запущенной от имени автора, DPAPI не защищает: она расшифрует ключ. Это совпадает с моделью угроз: компрометация машины автора — вне модели ([9](#9-модель-угроз)).
  - Ключ DPAPI живёт только в этой установке Windows: переустановка, смерть диска или сброс пароля учётки администратором (не смена пароля) — и рабочая копия не расшифруется. Поэтому резервная копия обязательна.
- **Резервные копии** — `flan-key-<номер>.flankey-backup` в каталоге, который автор указывает сам (флешка). Приватная часть зашифрована парольной фразой: PBKDF2-HMAC-SHA256 (600 000 итераций, соль 16 байт) → AES-256-GCM, всё через CNG. Фраза вводится в консоли без эха, дважды.
- **Защита от промахов:** `flan-build` не пишет ключ и резервные копии внутрь рабочего дерева git (ищет `.git` вверх по пути), не перезаписывает существующие файлы, а в `.gitignore` обоих репозиториев есть `*.flankey` и `*.flankey-backup`. Приватная часть не выводится на экран никогда.

**Смена ключа.**

- **Рабочий ключ потерян** (машина умерла, копий нет): `flan-build key restore` резервной копии запасного ключа → индекс подписывается им, все клиенты принимают его сразу. Следующий выпуск flan несёт ключи {запасной, новый запасной}; старые клиенты продолжают работать на бывшем запасном.
- **Рабочий ключ украден:** то же самое, и как можно скорее. По правилу шага 6 [6.1](#61-конверт-то-что-лежит-на-сервере) каждый клиент, принявший индекс нового ключа, больше не примет украденный. Клиенты, не синхронизировавшиеся с тех пор, уязвимы, пока не сделают `sync` или не обновят flan; атакующему для этого всё равно нужно подсунуть им индекс (взлом репозитория или MITM).
- **Потеряны или украдены оба ключа** — выпуск новой версии `flan` с новыми ключами, и пользователи ставят её вручную: старые клиенты новый индекс проверить не могут. Это осознанная цена простоты (без TUF-иерархии).

## 7. Клиент

### 7.1. Каталоги

Корень — `%FLAN_HOME%`, по умолчанию `%USERPROFILE%\.flan` (получаем через `SHGetKnownFolderPath(FOLDERID_Profile)` — Unicode). Переменная `FLAN_HOME` (с этапа 3) позволяет держать всё, например, на флешке. Она обязана быть абсолютным путём (`D:\flan`, `\\server\share\flan`); относительный путь — ошибка, иначе запуск из другого текущего каталога видел бы другую установку. Завершающий `\` отбрасывается. За пределы этой папки flan пишет только в одно место — `HKCU\Environment\Path` (см. [7.8](#78-path)); поэтому права администратора не нужны.

```
%FLAN_HOME%\
├── bin\                    ← единственное, что добавляется в PATH
│   ├── flan.exe            ← сам клиент (не прослойка)
│   ├── .shim.exe           ← эталонная прослойка, извлекается из ресурсов flan.exe
│   ├── rg.exe              ← жёсткая ссылка на .shim.exe (или копия, если не NTFS)
│   └── rg.shim             ← куда вести
├── apps\
│   └── ripgrep\
│       ├── 14.1.1\         ← содержимое архива (после extract_dir)
│       └── receipt         ← квитанция установки
├── cache\
│   └── <sha256>            ← скачанные архивы, адресуются содержимым
├── state\
│   ├── index.flan          ← последний принятый индекс
│   └── index.state         ← etag, generated_at, key_id
├── tmp\                    ← занятые прослойки, которые не удалось удалить (см. 7.4)
└── lock
```

**Пути.** Внутри flan пути — UTF-8 `std::string`: в UTF-8 и так индекс, квитанции, `.shim` и вывод. В UTF-16 их переводит одна функция слоя `io/fs` прямо перед вызовом ФС; она же добавляет префикс `\\?\` (снимает ограничение `MAX_PATH`), а сетевому пути — `\\?\UNC\`. Все вызовы ФС — W-функции; A-функции в клиенте запрещены (проверяется поиском по исходникам).

**Исключение — обход каталогов и удаление дерева:** они работают целиком на `std::wstring`, и имя, полученное от `FindFirstFileExW`, никогда не проходит через UTF-8. Имя в Windows может быть невалидным UTF-16 (непарный суррогат); после перевода туда и обратно путь указывал бы на другой файл или ни на какой. Если найденное имя нужно дальше как строка (имя пакета в `apps\`, команда в `bin\`), оно сначала проверяется в UTF-16 на ASCII-белый список (`isSafePackageName`, `isSafeName`) и только тогда сужается; остальные имена пропускаются.

**Запуск программ и `MAX_PATH`.** С файлами по путям любой длины flan работает (префикс `\\?\`), но Windows не запускает `.exe` по обычному пути в 260 символов и длиннее: `CreateProcessW` без `\\?\` отвечает `ERROR_PATH_NOT_FOUND`, с ним — запускает (проверено). Оболочки (cmd, PowerShell) префикс не ставят, поэтому команда из `bin\` запускается, только пока путь `bin\<cmd>.exe` короче 260 символов. Путь программы внутри `apps\` может быть и длиннее: прослойка запускает её с префиксом ([7.4](#74-прослойки-shim)). Отсюда практический предел `FLAN_HOME` — около 240 символов.

**Обход каталогов** — только `FindFirstFileExW(<каталог>\*, FindExInfoBasic)`, а нужные имена отбираются в коде. Других шаблонов нет: шаблоны `FindFirstFile` сопоставляются по старым правилам — `name.*` совпадает с `name`, `*.bat` совпадает с `foo.batch` через его короткое имя 8.3 `FOO~1.BAT`. `FindExInfoBasic` к тому же не возвращает коротких имён вовсе.

### 7.2. Сеть

Расширяем текущий `downloadFile`:

- **TLS:** явно `WINHTTP_OPTION_SECURE_PROTOCOLS = TLS1_2 | TLS1_3`. На Windows 7 WinHTTP по умолчанию TLS 1.2 не включает, а GitHub без него не работает. Где TLS 1.3 не поддерживается, флаг ставится без него. На Windows 7 без обновления KB3140245 не ставится и TLS 1.2 — тогда запрос падает с ошибкой TLS, и flan подсказывает это обновление (не проверяется: Windows 7 под рукой нет).
- **Прокси:** `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY` (Windows 8.1+), с откатом на `DEFAULT_PROXY`.
- **Таймауты:** соединение 15 с, приём 60 с между пакетами данных — на медленном канале медленно не значит мёртво.
- **Редиректы:** разрешены (GitHub Releases перекидывает на `objects.githubusercontent.com`), но только HTTPS → HTTPS (`WINHTTP_OPTION_REDIRECT_POLICY`).
- **Условный запрос индекса:** `If-None-Match: <etag>`. Ответ `304` → «индекс актуален», 0 байт тела.
  - ETag хранится в `state\index.state` вместе с URL источника и отправляется, только если источник тот же, а локальный индекс цел. После смены `FLAN_REPO` старый ETag не уходит.
  - ETag хранится и отправляется дословно — сильный или слабый (`W/"…"`).
  - Сервер не вернул ETag — ничего не храним, `sync` каждый раз качает целиком. Локальный `FLAN_REPO` копируется всегда: это дёшево.
- **Докачка архивов:** если в `cache\<sha256>.part` уже что-то есть — запрос `Range: bytes=N-`. Докачка безопасна, потому что в конце всё равно сверяется SHA-256.
  - `206` с `Content-Range: bytes N-(archive_size−1)/archive_size` → дописываем; `206` с другим началом или итогом → начинаем заново.
  - `200` → сервер `Range` не понял (так делает `codeload.github.com`): тело этого же ответа пишется с нуля.
  - `416` → `.part` удаляется, запрос без `Range`.
  - `.part` уже ровно `archive_size` (процесс убит после загрузки, до переименования) → запроса нет, только проверка хэша; `.part` больше `archive_size` → удаляется.
- **Повторы:** 1 + 3 попытки, паузы 2/5/10 с.
  - Повторяются: сетевые ошибки и таймауты; обрыв посреди тела — с `Range` от уже записанного; `5xx`, `408`, `429`. `Retry-After` в секундах учитывается, но не дольше 60 с.
  - Сразу ошибка: прочие `4xx` (в том числе `403` от GitHub при исчерпании лимита запросов — с понятным сообщением), ошибки TLS и сертификата, неверный URL, отказ в переадресации HTTPS → HTTP.
- **Хэш на лету:** SHA-256 обновляется прямо в цикле чтения. При докачке существующая часть хэшируется один раз перед продолжением. Второго прохода по файлу нет. Если после докачки хэш не совпал, `.part` выбрасывается и архив один раз качается целиком: так испорченный старый кусок отличается от настоящей подмены. Не совпал и тогда — код 4.
- **Лимиты:** `archive_size` из индекса известен заранее; больше этого размера не принимаем ни байта. `Content-Length` полного ответа, отличный от `archive_size`, — сразу ошибка целостности. Перед загрузкой — сообщение «будет скачано X МБ» и проверка свободного места: (`archive_size` − уже скачанное) + 16 МБ. Перед распаковкой — вторая проверка: распакованный размер из центрального каталога zip + 16 МБ (с этапа 3; до него распакованный размер неизвестен, и нехватка места при распаковке — обычная ошибка).
- **Проверка обрывов:** Debug-сборка читает `FLAN_DEBUG_DROP_AFTER=<байт>` и один раз рвёт загрузку после этого числа байт — так повтор с докачкой проверяется сквозным тестом на настоящем сервере. В Release-сборке этого кода нет (`#ifdef _DEBUG`).
- **Прогресс:** только если stdout — консоль (`GetConsoleMode`); при перенаправлении — одна строка в конце. Символы ASCII (`[#####-----]`), чтобы не ломаться на старых консольных шрифтах.

### 7.3. Распаковка

Своя, в процессе, на базе `tinfl` (inflate из miniz, ~25 КБ исходников). Поддерживаем zip: stored + deflate, ZIP64 — нет (архивы ≤ 512 МБ).

Каждое имя в архиве проверяется **до записи**. Здесь не белый список (в архивах бывают пробелы, скобки, `+`), а запреты:

- нет `..`-сегментов, абсолютных путей, букв дисков, `:` (альтернативные потоки NTFS);
- нет управляющих символов, точек и пробелов в конце сегмента, зарезервированных имён (`CON`, `NUL`, …);
- симлинки и записи-устройства отвергаются;
- суммарный распакованный размер ≤ 2 ГБ, коэффициент сжатия отдельной записи ≤ 1000 (защита от zip-бомб);
- CRC32 каждой записи проверяется;
- два имени, совпадающие без учёта регистра так, как его понимает NTFS (`CompareStringOrdinal` с `bIgnoreCase`), — отказ: в Windows это один файл, и второй молча затёр бы первый;
- перекрывающиеся данные записей (одни и те же байты архива под двумя именами — приём zip-бомб) — отказ;
- шифрование, ZIP64, многотомные архивы и методы сжатия, кроме stored (0) и deflate (8), — отказ. Записи с дескриптором данных (бит 3) допустимы: размеры и CRC берутся из центрального каталога, локальный заголовок с ним сверяется.

Имя записи без флага UTF-8 (бит 11) читается как CP437 — так поступает и Проводник. Файлы создаются с обычными атрибутами: «только чтение» и прочие атрибуты из архива не переносятся, время изменения не восстанавливается. Архив читается потоком (словарь 32 КБ), целиком в память не загружается.

`extract_dir` применяется при распаковке: записи вне него пропускаются, префикс срезается.

Почему не `tar.exe`: его нет на старых системах, он стартует отдельный процесс (заметно на Celeron + антивирус) и не позволяет проверить имена заранее; префикс он срезать умеет, но вслепую. А `tinfl` всё равно нужен для сжатого индекса. До этапа 3 распаковка шла через `System32\tar.exe`: архив целиком распаковывался в staging, и корнем приложения становился `staging\<extract_dir>`. Кроме того, `tar.exe` переводит пути в ANSI и на кириллическом пути не находил собственный архив. С этапа 3 (шаг 6) клиент распаковывает своим `zip.cpp`, и дочерних процессов при установке нет.

### 7.4. Прослойки (`shim`)

Отдельный крошечный `shim.exe` без CRT (только `kernel32`), вшитый в `flan.exe` как ресурс. В `bin\` лежит один эталон, а `rg.exe`, `fd.exe` и т.д. — жёсткие ссылки на него (на не-NTFS — копии).

`rg.shim` — текст UTF-8:

```
target=..\apps\ripgrep\14.1.1\rg.exe
package=ripgrep
```

Путь относительный к `bin\` — перенос `FLAN_HOME` ничего не ломает.

Поведение `shim.exe`:

1. Берёт собственное имя (`GetModuleFileNameW`), читает соседний `.shim`.
2. `CreateProcessW(target, <хвост GetCommandLineW() после argv[0]>)` — аргументы передаются **байт в байт**, без повторного разбора. Цель длиной от 260 символов передаётся в `lpApplicationName` с префиксом `\\?\` (`\\?\UNC\` для сетевого пути), иначе Windows её не запустит; `argv[0]` в командной строке остаётся обычным путём.
3. Наследует консоль и дескрипторы; создаёт Job Object с `KILL_ON_JOB_CLOSE` (убили прослойку — умер и ребёнок) и `SILENT_BREAKAWAY_OK`. Второй флаг оставляет в задании только самого ребёнка: без него, когда программа выходит, а прослойка закрывает задание, умирает и всё, что программа запустила и оставила работать (`code` открывает окно редактора и сразу выходит — окно закрылось бы). Если включить процесс в задание не удалось (на Windows 7 процесс, уже состоящий в чужом задании, в новое не входит), прослойка работает без него.
4. Игнорирует Ctrl+C у себя — обработчиком, который для `CTRL_C_EVENT` и `CTRL_BREAK_EVENT` возвращает TRUE; сигнал обрабатывает только сама программа. Не `SetConsoleCtrlHandler(NULL, TRUE)`: этот признак наследуется дочерним процессом, и программа тоже перестала бы видеть Ctrl+C (проверено: ребёнок такого родителя Ctrl+C не получил и вышел сам по таймауту; через прослойку с обработчиком программа выходит по Ctrl+C, а прослойка возвращает её код). Обработчики не наследуются.
5. Ждёт завершения и возвращает **тот же код выхода**.

`package=` нужен для конфликтов: если `bin\python.exe` уже принадлежит другому пакету, установка отказывает с понятной ошибкой.

- **Сборка:** без CRT, поэтому с `/GS-` — инициализировать защитную метку стека некому (исключение из [§10](#10-сборка-и-размер) только для прослойки); `memset`/`memcpy` свои — через `__stosb`/`__movsb`, иначе компилятор узнал бы в теле цикла `memset` и превратил его в рекурсивный вызов. Точка входа `ShimMain`, без `/RTC` и Just My Code (им нужен CRT). Размер — 6,5 КБ.
- **Эталон.** `bin\.shim.exe` сверяется с ресурсом работающего `flan.exe`. Отличается (вышла новая версия `flan`) — `flan setup` кладёт новый эталон и перевешивает на него все прослойки; отдельно установка и удаление пакетов эталон не обновляют.
- **Занятая прослойка.** Имя `.exe`, через которое сейчас работает программа, перезаписать нельзя, а переименовать можно. Удалить нельзя только последнее имя файла: имя жёсткой ссылки удаляется и при работающей программе, если на тот же файл есть другие ссылки (проверено), — так что обычно мешают только копии (не-NTFS, больше 1023 ссылок) и сам эталон. Поэтому прослойку, которую нужно убрать или заменить, flan сначала пытается удалить, а не вышло — переносит в `tmp\` под уникальным именем; содержимое `tmp\` удаляется в начале каждой меняющей команды под блокировкой. Вариант «удалить `.shim`, а `.exe` оставить» не годится: оставшийся `rg.exe` без `.shim` стал бы чужим и навсегда мешал бы установке.
- **Что в `bin\` прослойкой не считается:** `flan.exe`, `flan.exe.old`, `flan.exe.new`, `.shim.exe`. Их имена как команды пакета — конфликт.
- **Жёсткие ссылки:** на не-NTFS и после 1023 ссылок на файл (лимит NTFS) — копии эталона.
- **`.bat` больше не создаются** (решено на этапе 3, см. [13](#13-открытые-вопросы)). Код для `.bat` остаётся только для чтения и перехода: `install` и `uninstall` считают `bin\<cmd>.bat` с `rem package=<свой пакет>` своей прослойкой (удаляют её и учитывают при проверке конфликтов), а `flan setup` переводит на `shim.exe` все установленные пакеты по их квитанциям.

Известное ограничение: прослойка — консольное приложение, поэтому GUI-программа, запущенная через неё из Проводника, мигнёт консольным окном. В v1 ориентируемся на консольные утилиты (см. [13](#13-открытые-вопросы)).

### 7.5. Квитанция (`apps\<name>\receipt`)

Простой `key=value` в UTF-8, без JSON:

```
name=ripgrep
version=14.1.1
dir=14.1.1
arch=x64
sha256=<64 hex-символа — тот же, что в индексе>
bins=rg.exe
installed_at=2026-11-17T15:00:00Z
```

- **`dir`** — фактическое имя каталога версии внутри `apps\<name>\`. Оно может отличаться от `version` (см. [7.6](#76-транзакция-установки--обновления), шаг 6). `uninstall`, повторный `install` и удаление старой версии берут путь **только** из `dir` и никогда не собирают его из `version`.
- **`bins`** — через `;`, как в индексе.
- При чтении каждое значение проходит ту же проверку, что и при записи (`name`, `version`, `dir` — `isSafeName`; каждый элемент `bins` — `normalizeRelativePath`). Квитанция, где хоть одно значение не прошло проверку, считается повреждённой, и flan не берёт из неё пути.

Своя квитанция у каждого пакета — вместо общего `installed.json`. Установленные пакеты = обход `apps\*\receipt`. Повреждение одной квитанции не трогает остальные; запись атомарная (`receipt.tmp` → `MoveFileExW`).

### 7.6. Транзакция установки / обновления

Команды, меняющие состояние (`sync`, `install`, `uninstall`, позже `upgrade`, `cleanup`, `setup`), работают под файловой блокировкой `%FLAN_HOME%\lock`:

- Файл `lock` лежит постоянно. Блокировка — это его открытие через `CreateFileW` с нулевым share mode на всё время команды. Снимается закрытием дескриптора, в том числе когда процесс упал или убит: дескрипторы закрывает система.
- `ERROR_SHARING_VIOLATION` — блокировку держит другой `flan`: ждать до 10 с, потом выйти с кодом 6.
- `ERROR_ACCESS_DENIED` и любая другая ошибка — сразу понятное сообщение и код 1. Ждать бессмысленно: это права или атрибут «только чтение» на файле либо папке.
- `FILE_FLAG_DELETE_ON_CLOSE` не используется. С ним, пока система удаляет только что закрытый файл, второй процесс получает `ERROR_ACCESS_DENIED`, и «занято» становится неотличимо от настоящей ошибки прав.

Читающие команды (`list`, `installed`, позже `search`, `info`) работают без блокировки. Это безопасно, потому что всё, что они читают, — `state\index.flan` и квитанции — записывается атомарно: во временный файл, затем `MoveFileExW`. Читатель видит либо старую версию файла, либо новую, но никогда не половину. Худшее, что может случиться, — список на мгновение устареет относительно параллельной установки.

1. Найти запись в локальном индексе для архитектуры **ОС** (`GetNativeSystemInfo`), а не разрядности самого flan: на x64 — x64, если её нет, то x86; на x86 — только x86; на ARM64 — понятная ошибка «архитектура не поддерживается», без отката на x64/x86 (ARM64 пока только зарезервирован, см. §1).

   Оговорка про ARM64. Из x86- и x64-процесса `GetNativeSystemInfo` на ARM64 возвращает не ARM64, а эмулируемую архитектуру: x64, если система эмулирует x64 (Windows 11), иначе x86. Так что обещанная ошибка для ARM64 у наших сборок не сработает никогда, и flan поставит x64- или x86-пакет. Это безвредно: такой пакет на этой системе работает под той же эмуляцией, что и сам flan. Надёжно узнать архитектуру хоста можно через `IsWow64Process2` (параметр `pNativeMachine`). Она появилась в Windows 10 1709, поэтому её придётся загружать через `GetProcAddress`, чтобы не сломать 7 / 8.1. Понадобится, когда дойдём до ARM64.
2. Если квитанция есть и `sha256` совпадает — «уже установлено», выход. Если квитанция есть, а `sha256` другой, — это обновление: дальше те же шаги, а старая версия — каталог из `dir` её квитанции.
3. Есть `cache\<sha256>` и он цел → пропустить загрузку. Иначе — скачать в `cache\<sha256>.part` (с докачкой), сверить размер и SHA-256, переименовать. (С этапа 2. На этапе 1 кэша нет: архив качается в `tmp\` и удаляется после установки.)
4. Распаковать в `apps\<name>\.staging-<pid>\` своим `zip.cpp` ([7.3](#73-распаковка)): все имена проверяются до записи первого байта, свободное место — до распаковки, `extract_dir` применяется при распаковке, поэтому корень приложения — сам staging. Архив, отвергнутый правилами §7.3, или отсутствующий `extract_dir` — код 4; сбой диска или прав — код 1. (До этапа 3 — `tar.exe`, корень `staging\<extract_dir>`.)
5. Проверить, что все `bins` существуют и являются файлами.
6. Переименовать корень приложения → `apps\<name>\<dir>\`, где `dir = version`. Если такой каталог уже есть:
   - на него не указывает квитанция — это остаток прерванной установки, он удаляется, и `dir = version` (если удалить не удалось — как в следующем случае);
   - на него указывает квитанция (та же версия пересобрана с другим `sha256` или сменилась архитектура) — `dir = <version>-<первые 8 hex-символов sha256>`. Если занят и этот каталог — установка отказывает с понятной ошибкой.

   Остаток staging удаляется.
7. Записать прослойки (`.shim` атомарно, жёсткую ссылку — если её ещё нет; на этапах 1–2 — `.bat`, см. [12](#12-план-перехода)).
8. Записать квитанцию с фактическим `dir`. **Это точка фиксации**: до неё установка считается несостоявшейся.
9. Удалить каталог старой версии (путь — из `dir` старой квитанции). Если файл в нём занят (программа запущена) — оставить, записать в `state\pending-delete` и повторить при следующем запуске `flan`.

Сбой на шагах 3–7 → удаляется только staging; старая версия и её прослойки продолжают работать.

Если процесс убит, staging и недокачанный архив остаются на диске. Staging убирает следующий `install` этого пакета: под блокировкой другого `flan` нет, поэтому все `apps\<name>\.staging-*` заведомо мёртвые. А `cache\<sha256>.part` остаётся — с него продолжится загрузка.

**Политика кэша** (с этапа 2):

- `cache\<sha256>.part` живёт, пока загрузка не завершена.
- Готовый `cache\<sha256>` удаляется сразу после успешной установки (шаг 8): распакованное и так лежит в `apps\`. Лимит размера кэша поэтому не нужен.
- Если установка упала после загрузки, архив остаётся — повтор не качает его заново.
- Всё остальное чистит `flan cleanup` (этап 5).

**Занятость каталога** (шаги 6 и 9, `pending-delete`, `uninstall`) проверяется до удаления. Каждый файл внутри открывается на запись при полном совместном доступе (`OPEN_EXISTING`, файл не меняется). Если хоть один ответил `ERROR_SHARING_VIOLATION`, каталог занят и не трогается вовсе. Удалять по частям нельзя: работающая программа лишилась бы своих незаблокированных файлов, например `.py` рядом с `python.exe`. Другие признаки не годятся — проверено: открытие на чтение без совместного доступа работающий `.exe` пропускает (у загруженного образа нет открытого дескриптора), а каталог с ним Windows даёт переименовать.

Файл с атрибутом «только чтение» на запись не открывается вовсе: `ERROR_ACCESS_DENIED`, занят он или нет (проверено на работающей копии `cmd.exe`: с атрибутом — 5, без него — 32, `ERROR_SHARING_VIOLATION`). Поэтому у такого файла атрибут на время проверки снимается через дескриптор, открытый с `FILE_FLAG_OPEN_REPARSE_POINT`, и сразу возвращается; содержимое не меняется. Без этого удаление дерева, которое снимает атрибут перед удалением, начало бы удалять каталог с запущенной программой.

**Удаление дерева** (`staging`, каталоги версий, `uninstall`, `tmp\`) не проходит по ссылкам. Точка повторного анализа (junction, symlink) удаляется как сама ссылка — `RemoveDirectoryW` для каталога-ссылки, `DeleteFileW` для файла-ссылки, — а её цель не трогается. Признак берётся из атрибутов записи обхода и перед спуском в каталог перепроверяется на дескрипторе, открытом с `FILE_FLAG_OPEN_REPARSE_POINT`. С файлов и каталогов «только чтение» атрибут снимается перед удалением. Ни одно имя по пути не переводится в UTF-8 ([7.1](#71-каталоги)).

**Почему версионные каталоги, а не один фиксированный `apps\ripgrep\`:** файлы запущенной программы нельзя ни удалить, ни перезаписать. (Сам каталог Windows 10/11 переименовать даёт, и программа продолжает работать, — но очистить его всё равно нельзя.) Версионный каталог позволяет обновлять программу, пока она работает. «Стабильный путь» для пользователя — это `bin\rg.exe`, а не путь внутри `apps\`.

Для программ, хранящих настройки рядом с собой, позже появится поле `persist` (что переносить из старой версии в новую). В v1 его нет.

### 7.7. Команды

| Команда | Что делает |
|---|---|
| `flan sync` | Обновить индекс (условный запрос). |
| `flan search [текст]` | Поиск по имени и описанию; без аргумента — все пакеты. |
| `flan info <pkg>` | Версия, описание, размер загрузки, установлен ли. |
| `flan install <pkg>…` | Установить. Если пакет уже установлен, но `sha256` в индексе другой, — обновить (транзакция [7.6](#76-транзакция-установки--обновления)). Если индекса нет — сначала `sync`. Если индекс старше 7 дней — предупреждение. |
| `flan uninstall <pkg>…` | Удалить прослойки, квитанцию, каталог. Прослойки находятся по владельцу (`package=`), а не по квитанции: так удаляется и пакет с повреждённой квитанцией, а чужие прослойки не трогаются никогда. |
| `flan upgrade [pkg…]` | С этапа 4. Без аргументов — все установленные пакеты, у которых `sha256` в индексе отличается от квитанции, и последним — сам flan, если `sha256` в индексе отличается от `bin\flan.exe`. С аргументами — указанные (`flan` среди них — самообновление, [7.9](#79-самообновление)). Каждый пакет — та же транзакция [7.6](#76-транзакция-установки--обновления), что у `install`. Сбой одного не останавливает остальные; код возврата — первой неудачи. Пакет, которого нет в индексе, пропускается с предупреждением (без аргументов) или даёт код 5 (указан явно). |
| `flan list` | Установленные пакеты. **Меняет текущую семантику** — на этапе 5, вместе с появлением `search`, чтобы ни на одном этапе не пропадал способ увидеть доступные пакеты. До этого `list` показывает доступные (из индекса), а установленные — `flan installed`. |
| `flan cleanup` | Очистить `cache\` и неудалённые старые версии. |
| `flan setup` | Добавить `bin\` в PATH пользователя, скопировать себя в `bin\`. `--remove` — обратное. |

Флаги: `--no-progress`, `--help`, `--version` (с этапа 4: `flan 0.4.0 (x64)`; версия та же, что в VERSIONINFO ресурсов `flan.exe`). Больше пока не нужно.

`flan` — особый пакет ([7.9](#79-самообновление)): `install flan` подсказывает `flan upgrade flan`, `uninstall flan` отказывает с подсказкой про `flan setup --remove`, а `installed` его не показывает — версию сообщает `flan --version`.

Коды возврата: `0` — успех, `1` — прочая ошибка, `2` — неверные аргументы, `3` — сеть, `4` — целостность (хэш, подпись, откат индекса), `5` — пакет не найден, `6` — занята блокировка. Вводятся на этапе 1 для всех переписанных команд.

### 7.8. PATH

`flan setup` правит `HKCU\Environment\Path` напрямую:

- читает значение **без раскрытия** переменных и целиком, какой бы длины оно ни было, и сохраняет исходный тип (`REG_EXPAND_SZ` / `REG_SZ`);
- добавляет каталог `bin\`, только если его там ещё нет:
  - в `REG_EXPAND_SZ` — как `%USERPROFILE%\.flan\bin`, если `FLAN_HOME` не задан и эта запись после раскрытия действительно указывает на наш `bin\` (иначе — например, при подменённом `USERPROFILE` — абсолютным путём); при заданном `FLAN_HOME` — абсолютным путём;
  - в `REG_SZ` — всегда абсолютным путём: там `%…%` не раскрывается;
  - значения `Path` нет — создаётся `REG_EXPAND_SZ`;
  - `Path` другого типа (не `REG_SZ`/`REG_EXPAND_SZ`) не трогается — понятная ошибка;
- «уже есть» — сегменты через `;` сравниваются после раскрытия переменных, без учёта регистра, без завершающего `\` и обрамляющих кавычек; пустые сегменты и всё остальное сохраняются байт в байт. Значение правится как UTF-16, без перевода в UTF-8;
- после изменения — и только после него — рассылает `WM_SETTINGCHANGE` с `"Environment"` через `SendMessageTimeoutW` и напоминает, что PATH увидят только новые окна консоли.

**Проверка записи.** Debug-сборка читает `FLAN_DEBUG_ENV_HIVE=<файл>`: тогда `Environment\Path` живёт в частном кусте реестра (`RegLoadAppKeyW`), а настоящий реестр не трогается вовсе — так запись и `--remove` проверяются на любом PATH. В Release-сборке этого кода нет (`#ifdef _DEBUG`), как и у `FLAN_DEBUG_DROP_AFTER`.

`flan setup --remove` удаляет из `Path` все сегменты, совпавшие с `bin\` по тем же правилам, остальное оставляет байт в байт. Папку `FLAN_HOME` он не трогает.

**Копия себя.** `flan setup` кладёт работающий `flan.exe` в `bin\flan.exe`. Если запущен уже сам `bin\flan.exe` (сравниваются идентификаторы файлов, а не строки путей: мешают регистр, короткие имена, жёсткие ссылки), копировать нечего. Иначе новый файл пишется в `bin\flan.exe.new`, существующий `bin\flan.exe` переименовывается в `flan.exe.old` (работающий `.exe` переименовать можно), `.new` встаёт на его место. `flan.exe.old` удаляется при следующем запуске любой команды — тот же механизм, что в [7.9](#79-самообновление). Затем `setup` обновляет эталон прослоек и переводит `.bat` на `shim.exe` ([7.4](#74-прослойки-shim)).

**Длинный путь `bin\`.** В конце `setup` меряет самый длинный путь `bin\<команда>.exe` — среди `flan` и команд установленных пакетов, в символах UTF-16. Windows не запускает программу по обычному пути в 260 символов и длиннее ([7.1](#71-каталоги)), поэтому:

- путь от 260 символов — предупреждение со списком команд, которые не запустятся из консоли;
- путь от 240 символов (на имя команды длиннее нынешних остаётся меньше 20 символов) — предупреждение с длиной самого длинного имени, которое ещё запустится;
- в обоих случаях — что делать: `flan setup --remove`, перенести папку `FLAN_HOME` в короткую (например, `C:\flan`), задать там `FLAN_HOME` и запустить `flan setup` из нового `bin\`. Пути прослоек относительные, перенос их не ломает.

Это только предупреждение: код выхода не меняется, сами файлы flan по длинным путям работают.

`setx` не используется: он обрезает значение до 1024 символов и раскрывает переменные. Окно «Переменные среды» тоже не выход: значение длиннее 2047 символов оно не сохраняет. Поэтому `flan setup` пишет в реестр сам — и обязан работать с PATH любой допустимой длины.

### 7.9. Самообновление

`flan` — пакет в индексе (`kind = exe`, `bin = flan.exe`, сборки x64 и x86 из выпусков `muirbil/flan` на GitHub, [5.3](#53-правила-приёма-пакетов)). Но ставится он не в `apps\`: сам flan — это `bin\flan.exe`, без прослойки и квитанции. `flan upgrade flan` под блокировкой:

1. находит запись `flan` для архитектуры ОС (как [7.6](#76-транзакция-установки--обновления), шаг 1) и сравнивает её `sha256` с SHA-256 файла `bin\flan.exe` — не запущенного образа: запущен может быть flan из папки сборки. Совпадают — «уже последняя версия», файлы не трогаются;
2. скачивает файл в `cache\<sha256>` тем же путём, что любой пакет: докачка, размер, SHA-256 из подписанного индекса;
3. копирует его в `bin\flan.exe.new` и запускает `bin\flan.exe.new --version` (таймаут 10 с): код должен быть 0, а версия — как в индексе. Иначе `.new` удаляется, а прежний flan остаётся. Запускать скачанный файл можно — его хэш подписан, — зато сломанная или чужая сборка не встанет на место рабочей;
4. заменяет `bin\flan.exe` той же функцией, что `flan setup` ([7.8](#78-path), «Копия себя»): работающий `bin\flan.exe` переименовывается в `flan.exe.old` (переименовать работающий `.exe` можно, перезаписать — нет), `.new` встаёт на его место, сбой второго переименования возвращает первое. Если `flan.exe.old` ещё занят прошлым запуском — понятный отказ, ничего не меняется;
5. `flan.exe.old` удаляется при следующем запуске любой команды, архив в `cache\` — сразу.

Эталон прослоек новый flan сверяет со своим `shim.exe` в начале каждой изменяющей команды и при отличии обновляет — тем же кодом, что `setup` ([7.4](#74-прослойки-shim)). Дочерний `flan setup` после замены не запускается: он заново добавил бы `bin\` в PATH тому, кто сознательно убрал его через `--remove`.

Между двумя переименованиями шага 4 `bin\flan.exe` на мгновение нет. Если именно тогда пропадёт питание, останется `bin\flan.exe.old`: его можно запустить как `flan.exe.old setup`, и он вернёт себя на место.

### 7.10. Вывод и ошибки

- Без `<iostream>`. Свой маленький слой: `WriteConsoleW` для консоли, `WriteFile` с UTF-8 при перенаправлении.
- Ошибки — коды возврата функций (`enum class Error` + сообщение), не исключения. Клиент собирается **без исключений C++** (`/EHs-c-`, `_HAS_EXCEPTIONS=0`): ни одного `catch` в нём нет, так что нехватка памяти и раньше завершала процесс через `std::terminate`, и поведение не меняется, а поддержка исключений весила ~25 КБ ([10](#10-сборка-и-размер)).
- Никаких `std::filesystem`: всё нужное есть в `io/fs.cpp` поверх W-функций.

## 8. `flan-build` (генератор)

Отдельный проект в том же решении, на C++, общий код с клиентом. Ему можно всё: `nlohmann/json`, `<iostream>`, `<filesystem>` — размер не важен.

| Команда | Что делает |
|---|---|
| `flan-build check packages\` | Проверка манифестов без сети: схема, имена, уникальность, `{version}` раскрывается. |
| `flan-build hash packages\ripgrep.json [--force]` | Скачивает архивы, вписывает `sha256`, проверяет `extract_dir` и `bin` внутри архива. |
| `flan-build index packages\ -o index.flan [--key <путь>]` | Полная проверка + сборка + сжатие + подпись. Без `--key` — рабочая копия с наибольшим номером в `%LOCALAPPDATA%\flan-build\` (какая — пишется в выводе). До этапа 4 индекс собирался с `key_id = 0`, до этапа 2 — без сжатия. |
| `flan-build keygen --backup <каталог> [--id N] [--key <путь>]` | Новая пара ключей N (по умолчанию 1) и запасная N+1. Рабочая копия N — под DPAPI; резервные копии обоих — в `<каталог>` под парольной фразой. На экран — только открытые ключи как C-массивы для `keys.hpp` и их отпечатки. |
| `flan-build key restore <копия> [--key <путь>]` | Рабочая копия под DPAPI из резервной (новая машина, переход на запасной ключ). |
| `flan-build key check [--key <путь>] [--backup <копия>]` | Расшифровывает рабочую копию (и резервную, если указана) и проверяет пробной подписью, что открытый ключ — тот, что в `keys.hpp`. |

**Подпись индекса.** `index` подписывает SHA-256 от первых 24 байт конверта и тела ([6.1](#61-конверт-то-что-лежит-на-сервере)) и до записи файла проверяет подпись открытым ключом с тем же номером из `keys.hpp`: индекс, подписанный ключом, которого клиенты не знают, не выйдет. Номер ключа не может быть меньше, чем у предыдущего `index.flan`, — такой индекс клиенты отвергли бы. Предыдущий индекс проверяется подписью, если он подписан; неподписанный (`key_id = 0`) принимается только как предыдущий — так первый подписанный индекс собирается поверх последнего неподписанного.

**Парольная фраза** вводится в консоли без эха. Если стандартный ввод перенаправлен, Release-сборка отказывает («введите фразу в консоли»), а Debug-сборка читает строку из него — только ради сквозных проверок на тестовых ключах.

Для каждого архива генератор **реально** проверяет, что он открывается тем же `zip.cpp`, что и у клиента, что `extract_dir` существует, а каждый `bin` — файл. До этапа 3, пока своего `zip.cpp` нет, содержимое архива проверяется через `System32\tar.exe -tf` — тем же `tar.exe`, которым распаковывает клиент.

Для `kind = exe` архива нет — вместо этого генератор проверяет заголовок PE: сигнатуры `MZ` и `PE\0\0`, флаг исполняемого образа и отсутствие флага DLL, а поле `Machine` должно соответствовать ключу `arch` (`0x8664` — x64, `0x014C` — x86, `0xAA64` — arm64). Так ловится и опечатка «в `x86` положили ссылку на amd64-сборку».

Скачанные архивы кэшируются локально по `sha256` (в `.cache\`, не коммитится), поэтому повторная сборка индекса сеть не трогает.

**Когда `hash` вправе вписать хэш.** Генератор сверяется с предыдущим `index.flan` в корне репозитория пакетов, рядом с `packages\`:

- запись `(name, arch)` в предыдущем индексе с **тем же URL**, но хэш скачанного архива другой → **ошибка**: апстрим подменил файл под той же ссылкой;
- URL изменился (новая версия) или записи в предыдущем индексе нет → вписать новый хэш;
- `--force` — принять новый хэш и при том же URL, когда апстрим законно перезалил файл. В выводе — явное предупреждение со старым и новым хэшем.

`hash` идемпотентен: если ни один хэш не изменился, файл манифеста не перезаписывается вовсе. Если записать нужно, сохраняются переводы строк и BOM исходного файла — иначе при `core.autocrlf` каждый запуск менял бы рабочую копию. Форматирование при первой записи выравнивается (отступ 2 пробела, массивы — по элементу на строку); порядок полей и шаблоны `{version}` остаются как у автора.

`generated_at` = текущее время, но не меньше, чем в предыдущем `index.flan` + 1.

## 9. Модель угроз

| Угроза | Защита |
|---|---|
| Подмена индекса (взлом репозитория, токена, MITM) | Подпись ECDSA; ключ не на GitHub. |
| Подсовывание старого подписанного индекса с уязвимой версией | `generated_at` не может уменьшаться. |
| Кража ключа подписи, о которой автор узнал | Переход на запасной ключ: клиент, принявший его индекс, больше не принимает старый ключ и снимает «заморозку» индексом из будущего ([6.1](#61-конверт-то-что-лежит-на-сервере), шаг 6). |
| Подмена `flan.exe` при самообновлении | SHA-256 из подписанного индекса; новый `flan.exe` проверяется запуском `--version` до замены. |
| Подмена архива у апстрима или в пути | SHA-256 из подписанного индекса, проверка до распаковки. |
| Обход каталога через имена (`..\`, `C:\`, `CON`, ADS) | Белый список для имён пакетов и `bin`; запреты для имён внутри архивов; всё в одном `validate.hpp`. |
| Zip-бомба, бесконечный поток | Лимиты размеров на загрузку, распаковку, коэффициент сжатия. |
| Подмена `tar.exe` / поиск в текущем каталоге | Внешних процессов при установке нет совсем. |
| Порча состояния при сбое или параллельном запуске | Блокировка, атомарные переименования, квитанции по пакетам. |
| Выполнение кода пакета при установке | Не поддерживается в принципе: нет скриптов, нет установщиков. |
| Перехват команды чужим пакетом (`bin\python.exe`) | Владелец прослойки записан в `.shim`; конфликт = отказ. |

Вне модели: вредоносная программа, которую апстрим сам опубликовал под своей подписью; компрометация машины автора вместе с приватным ключом.

## 10. Сборка и размер

Release:

- `/O1` (минимум размера: на Celeron узкое место — диск и сеть, а не процессор), `/GL`, `/Gy`, `/LTCG`, `/OPT:REF`, `/OPT:ICF`
- **«Гибридный» CRT:** `/MT`, но Universal CRT берётся из Windows — `ucrt.lib` вместо `libucrt.lib` (`/NODEFAULTLIB:libucrt.lib`), а `vcruntime` остаётся статическим. VC++ Redistributable по-прежнему не нужен: `ucrtbase.dll` (через `api-ms-win-crt-*`) — часть Windows 10/11, а в 7 SP1/8.1 его ставит обновление KB2999226. Без этого обновления `flan.exe` на 7/8.1 не запустится («api-ms-win-crt-runtime-l1-1-0.dll не найден») — это принятая цена (см. [13](#13-открытые-вопросы), вопрос 1). Статический UCRT весил ~94 КБ.
- без исключений C++: `/EHs-c-`, `_HAS_EXCEPTIONS=0` ([7.10](#710-вывод-и-ошибки))

## 11. Тестирование

- **Модульные:** `validate.hpp` (таблица хороших и плохих имён), разбор индекса, `zip.cpp`, разбор `.shim` и квитанций, правка PATH (значение длиннее 2047 символов), удаление дерева (junction наружу, «только чтение», имя с непарным суррогатом), обход `bin\` при файле вроде `rg.batch` с коротким именем.
- **Вредоносные входы:** набор zip-файлов (`..\`, абсолютные пути, ADS, симлинки, бомба, битый CRC, обрезанный архив) и индексов (обрезанный, с неверными смещениями, с неверной подписью, со старым `generated_at`). Всё должно отвергаться с понятной ошибкой, без падения.
- **Фаззинг:** `/fsanitize=fuzzer` (MSVC) для разбора индекса и zip.
- **Сквозной:** тестовый ключ + локальный каталог `FLAN_REPO` с индексом; сценарий `sync → install → upgrade → uninstall`, плюс обрыв загрузки посередине и докачка. Самообновление — двумя Debug-сборками с разными версиями: старая заменяет себя, пока работает она сама и пока второй её экземпляр держит образ; занятый `flan.exe.old`; неверный хэш; версия в `--version` не как в индексе; запуск из папки сборки. Смена ключа — индексами тестовых ключей 240 и 241.
- **Ручной чек-лист перед релизом:** настоящий пользователь с кириллическим именем — `SHGetKnownFolderPath` и PATH с `%USERPROFILE%` (учётную запись один раз создаёт администратор: `net user <имя> /add`; на этапе 3 кириллица проверена только через `FLAN_HOME`), путь длиннее 260 символов, FAT32-флешка как `FLAN_HOME`, 32-битная Windows, запущенная программа во время `upgrade`, `flan upgrade flan` с настоящего выпуска на GitHub, `flan-build key check --backup` для каждой резервной копии ключа (сразу после `keygen` и раз в год), PATH пользователя длиннее 2047 символов для `flan setup` (такой PATH есть у автора; окно «Переменные среды» его не сохраняет).
- **`flan setup` и настоящий `HKCU`:** проверен **только на чтение**. На этапе 3 Release-сборка прочитала PATH автора (2161 символ, `REG_EXPAND_SZ`), нашла в нём `%USERPROFILE%\.flan\bin` и ничего не записала: экспорт `HKCU\Environment` до и после совпал байт в байт. Запись и `--remove` проверены только на частном кусте (`FLAN_DEBUG_ENV_HIVE`, [7.8](#78-path)) — на PATH той же длины. Полный цикл записи на настоящем `HKCU` сознательно не делался: испорченный PATH длиннее 2047 символов окном Windows не починить.

## 12. План перехода

Каждый этап заканчивается работающим `flan install ripgrep` от начала до конца.

**Этап 0 — зафиксировать текущее.**
`git pull` (локальная ветка отстаёт на коммит с README), закоммитить сделанные исправления как есть. Это точка отката.

**Этап 1 — один источник правды.**
- Раскладка исходников по [§4](#4-компоненты-и-раскладка-исходников) — первым шагом, только переносы.
- `flan-build`: `check`, `hash` (с правилами и `--force` из [§8](#8-flan-build-генератор)), `index` без подписи и сжатия. Содержимое архивов проверяется через `tar.exe -tf`.
- Формат индекса 2: `compression = 0`, `key_id = 0`, подпись нулевая и не проверяется.
- `FLAN_REPO` ([§5.1](#51-раскладка)): проверка до публикации — на локальном клоне `flan-packages`.
- Версионные каталоги, квитанции с `dir=`, транзакция [§7.6](#76-транзакция-установки--обновления) без кэша, блокировка, коды возврата.
- `.bat`-прослойки пока остаются. Вторая строка (после `@echo off`) — `rem package=<name>`: установка отказывает, если `.bat` с тем же именем принадлежит другому пакету, а `uninstall` не трогает чужие. Третья — `"<путь к .exe>" %* & call exit /b %%errorlevel%%`, вызов и выход на одной строке:
  - `cmd.exe` перечитывает `.bat` с прежнего смещения после возврата из программы, и при обновлении работающей прослойки выполнил бы хвост новой строки как команду (воспроизведено);
  - `& exit /b` без числа теряет код возврата программы, а `%errorlevel%` раскрылся бы ещё при разборе строки, до запуска; `call` раскрывает `%%errorlevel%%` повторно — после завершения программы;
  - `%` в пути к `.exe` удваивается.
- Команды: `list` — доступные пакеты, `installed` — установленные (смена семантики `list` — на этапе 5).
- В `flan-packages`: `packages/ripgrep.json` с настоящим SHA-256, удалить `core.flan` и `meta/`.
- PATH: `flan setup` появится только на этапе 3, поэтому на этапе 1 `%USERPROFILE%\.flan\bin` добавляется в PATH пользователя вручную, через окно «Переменные среды» (`rundll32 sysdm.cpl,EditEnvironmentVariables`). Не через `setx` — он обрезает значение и раскрывает переменные ([§7.8](#78-path)).

*Готово, когда:* на чистом `%USERPROFILE%\.flan` работают `flan sync`, `flan install ripgrep` и `rg --version` с настоящим SHA-256 в манифесте. Сначала проверяется через `FLAN_REPO` на локальный клон, затем — против GitHub после публикации `flan-packages`.

**Между этапами 1 и 2 — `kind = exe`.**
Пакеты из одиночного `.exe` (jq и подобные) по правилам §5.2. Формат индекса не меняется: поле `kind` в нём уже есть. Генератор проверяет заголовок PE (§8); клиент вместо распаковки переносит проверенный файл в staging под именем из `bin`, дальше транзакция §7.6 без изменений. Клиенты этапа 1 такой индекс принимают, а на `install` пакета с `kind = exe` отвечают понятной ошибкой.
*Готово, когда:* `flan install jq && jq --version` работает (x64 и x86).

**Этап 2 — медленный интернет.**
`tinfl`, сжатый индекс, `If-None-Match`, докачка, хэш на лету, кэш по `sha256`, `archive_size` — и весь остальной §7.2 (TLS, прокси, таймауты, переадресации, ASCII-прогресс): это тот же переписываемый сетевой слой. Сжатый индекс клиенты этапа 1 не читают («compressed index is not supported») — принято: других пользователей нет, а автор обновляет свой `flan.exe` до публикации сжатого индекса.
*Готово, когда:* повторный `sync` передаёт 0 байт тела; обрыв на 50% архива и повторный `install` докачивают только остаток.

**Этап 3 — без лишнего веса.**
Своя распаковка вместо `tar.exe` (и в клиенте, и в `flan-build`), Unicode-пути, `FLAN_HOME`, `shim.exe`, удаление `iostream`, `filesystem` из клиента (`nlohmann` в клиенте нет с этапа 1). `flan setup`. Каждая замена — отдельным шагом, с размером `flan.exe` (Release, x64 и Win32) после каждого; первым шагом — флаги сборки [§10](#10-сборка-и-размер), чтобы вклад остальных мерился уже с ними.

До появления `flan setup` разработчик копирует собранный `flan.exe` в `.flan\bin` вручную. `setup` должен заменить этот шаг целиком, включая обновление копии в `bin\` после пересборки: повторный `flan setup` из нового `flan.exe` кладёт его на место старого (через переименование работающего, как в [§7.9](#79-самообновление)).

*Готово, когда:* x64 Release ≤ 200 КБ; всё работает с `FLAN_HOME` на кириллическом пути длиннее 260 символов (а системная кодовая страница ANSI кириллицы не содержит). Проверка на настоящем пользователе с кириллическим именем — в ручном чек-листе [§11](#11-тестирование).

*Итог этапа 3:* x64 Release — 185 856 байт (Win32 — 147 456), `shim.exe` — 7 168. С `FLAN_HOME` на кириллическом пути в 292 символа (ACP 1252) все команды flan работают — `sync`, `install` и `uninstall` всех пяти пакетов, `installed`, `setup` и `setup --remove` (на частном кусте). Запустить установленные команды по такому пути нельзя ни через прослойку, ни напрямую: это предел Windows для пути самого `.exe` (см. [7.1](#71-каталоги), «Запуск программ и `MAX_PATH`»); прослойка из короткого `bin\` запускает цель длиннее 260 символов, а `setup` предупреждает, когда путь `bin\` к этому пределу подходит ([7.8](#78-path)). Отступления, принятые по ходу: гибридный CRT и Windows 7/8.1 только с KB2999226 ([10](#10-сборка-и-размер), [13](#13-открытые-вопросы)), клиент без исключений C++ ([7.10](#710-вывод-и-ошибки)), Ctrl+C в прослойке — обработчиком, а не `SetConsoleCtrlHandler(NULL, TRUE)` ([7.4](#74-прослойки-shim)).

**Этап 4 — доверие.**
Подпись ([6.3](#63-подпись-и-ключи)), ключи и команды `flan-build` для них ([8](#8-flan-build-генератор)), защита от отката по номеру ключа и `generated_at` ([6.1](#61-конверт-то-что-лежит-на-сервере), шаг 6), `flan --version`, общий `flan upgrade [pkg…]` ([7.7](#77-команды); перенесён с этапа 5) и самообновление ([7.9](#79-самообновление)). Всё проверяется на Debug-сборках с тестовыми ключами; настоящие ключи автор создаёт сам, в своей консоли (фраза вводится без эха), после чего их открытые части вносятся в `keys.hpp`, собирается Release `0.4.0`, автор публикует выпуск `v0.4.0` (`flan-x64.exe`, `flan-x86.exe`), а в `flan-packages` появляются `packages/flan.json` и первый подписанный индекс.

Клиент этапа 3 подписанный индекс отвергает («signed with key 1, unknown to this version»), а клиент этапа 4 — неподписанный. Поэтому автор обновляет свой `flan.exe` через `flan setup` из новой сборки до публикации подписанного индекса, а между этим и публикацией `flan sync` с GitHub даёт код 4 — как при переходе на сжатый индекс на этапе 2.

*Готово, когда:* изменённый вручную байт в `index.flan` даёт код возврата 4.

**Этап 5 — рост репозитория.**
`search`, `info`, `cleanup`; 20–30 популярных консольных утилит (fd, bat, jq, fzf, 7zip, …); CI, который запускает `flan-build check` на PR.
