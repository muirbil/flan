# flan — DESIGN

> Статус: черновик v2 дизайна. Описывает, **каким flan должен стать**, а не каким он является сейчас.
> Текущее состояние кода разобрано в разделе [2](#2-что-есть-сейчас-и-что-с-этим-не-так), план перехода — в [12](#12-план-перехода).

## 1. Зачем flan и чем он не является

**flan** — пакетный менеджер для Windows, который ставит **портативные** программы (zip-архив или одиночный `.exe`) в каталог пользователя, без прав администратора.

### Цели (в порядке приоритета)

1. **Лёгкость.** Один `flan.exe` без зависимостей (ни .NET, ни PowerShell, ни VC++ Redistributable). Целевой размер — **≤ 200 КБ** (x64 Release), желательно ≤ 150 КБ. Самообновление должно скачиваться за секунды даже на медленном канале.
2. **Медленный и нестабильный интернет.** Ничего не качать повторно: условные запросы, докачка, кэш по хэшу, сжатый индекс.
3. **Слабое железо** (Celeron, HDD, 4 ГБ RAM). Один проход по файлу, никаких дочерних процессов на горячем пути, без загрузки всего в память там, где этого можно избежать.
4. **Безопасность по построению.** Всё, что пришло из сети, — недоверенные данные. Установка никогда не запускает код пакета.
5. **Простота.** Код должен помещаться в голове одного человека.

### Не-цели (сознательно)

| Не делаем | Почему |
|---|---|
| MSI / NSIS / Inno-установщики | Это запуск чужого кода с непредсказуемыми последствиями. flan ставит только то, что можно распаковать. |
| Права администратора, установка «для всех пользователей», службы | Противоречит модели «всё в профиле пользователя» (см. ниже). |
| Разрешение зависимостей | Портативные программы почти никогда их не требуют. Поле зарезервировано на будущее (см. [13](#13-открытые-вопросы)). |
| GUI | Только консоль. |
| Скрипты установки в манифестах | Причина та же, что у установщиков. |

### Без прав администратора

flan **никогда** не требует прав администратора и не вызывает окно UAC. Всё, что он создаёт, находится в одной папке внутри домашнего каталога пользователя — `$HOME\.flan` (`%USERPROFILE%\.flan`), а этой папкой пользователь и так владеет полностью.

Следствия для дизайна:

| Куда пишет flan | Куда **не** пишет |
|---|---|
| `%USERPROFILE%\.flan\` — программы, прослойки, кэш, состояние | `C:\Program Files`, `C:\Windows`, корень диска |
| `HKCU\Environment\Path` — PATH текущего пользователя | `HKLM` — системный PATH и любые машинные настройки |
| — | службы, планировщик задач, драйверы, ассоциации файлов |

- В `flan.exe` и `shim.exe` вшит манифест с `requestedExecutionLevel level="asInvoker"`. Без него Windows может сама запросить повышение прав у 32-битного `.exe`, в имени которого есть `install`, `setup` или `update` (так работает эвристика Installer Detection).
- Если flan всё же запустили от имени администратора, он выводит предупреждение: в этом нет смысла, а файлы, созданные повышенным процессом, могут потом мешать обычному.
- Отсюда же портативность: папку можно перенести через `FLAN_HOME` (например, на флешку), а удаление flan целиком — это `flan setup --remove` и удаление одной папки.
- Отсюда же граница возможностей: всё, что требует прав администратора (установщики MSI, службы, драйверы), flan не ставит по определению.

### Поддерживаемые платформы

- **Официально:** Windows 10 / 11, x64 и x86.
- **Без гарантий:** Windows 7 SP1 / 8.1. Мы не тестируем их, но и не используем API, которые их ломают без нужды (см. TLS 1.2 в [7.2](#72-сеть)).
- ARM64 — зарезервирован в формате, не собирается.

## 2. Что есть сейчас и что с этим не так

Исходная точка — локальная ветка с исправлениями уязвимостей (ещё не закоммичена). Эти исправления правильные и переносятся в новый дизайн: белый список имён (`validate.hpp`), проверка границ при разборе базы, загрузка только по HTTPS с лимитом размера и записью через `.part`, запуск `tar.exe` по явному пути без оболочки.

Ниже — проблемы, которые точечными правками не решаются, потому что они в самой архитектуре.

| # | Проблема | Следствие |
|---|---|---|
| A1 | **Два источника правды**: `core.flan` (имя → id) и `meta/<id>.json` (всё остальное) поддерживаются вручную | id разъезжаются (`ripgrep` → id 1, файл `meta/101.json` → 404). `flan install` сейчас не работает ни для одного пакета. |
| A2 | Установка = **2 сетевых запроса** (метаданные + архив) | Лишний round-trip на медленном канале; метаданные не покрыты ничем, кроме HTTPS. |
| A3 | Индекс ничем не подписан | Кто контролирует репозиторий (или токен GitHub), тот контролирует, что запустится у пользователя. SHA-256 архива защищает только от порчи в пути, но не от подмены самих метаданных. |
| A4 | `hash_v` и `timestamp` в формате есть, но не используются; комментарии со смещениями в `CoreHeader` не совпадают с реальной раскладкой (magic на 8, а не на 0, и т.д.) | Формат живёт без спецификации. |
| A5 | `nlohmann/json` (950 КБ заголовка), `<iostream>`, `<filesystem>` в клиенте | x64 Release весит ~430 КБ, Win32 ~365 КБ — в 2–3 раза больше цели. |
| A6 | Все пути через ANSI-функции (`SHGetFolderPathA`, `CreateDirectoryA`, `DeleteFileA`) | Ломается на кириллическом имени пользователя; нет поддержки путей длиннее `MAX_PATH`. |
| A7 | Распаковка через `System32\tar.exe` | Нет на Windows до 10 1803; отдельный процесс на каждую установку; нельзя проверить имена внутри архива до записи. (Срезать верхнюю папку архива `tar.exe` умеет — это bsdtar с `--strip-components`, — но только вслепую, не глядя, что внутри.) |
| A8 | `.bat`-прослойки | Вызов `.bat` из другого `.bat` без `call` молча обрывает вызывающий скрипт; Ctrl+C даёт «Завершить выполнение пакетного файла [Y/N]?»; `%` и `^` в аргументах могут перетолковываться; в прослойке зашит абсолютный путь. |
| A9 | Повторный `install` распаковывает поверх существующего каталога | Файлы старой версии смешиваются с новой. Нет обновления как такового. |
| A10 | `installed.json` — один файл, переписывается целиком, без блокировки | Два параллельных `flan` портят реестр; сбой посреди записи теряет все записи. |
| A11 | SHA-256 считается **вторым проходом** после загрузки; оборванная загрузка начинается заново | Двойное чтение с HDD; на плохом канале большой архив может не скачаться никогда. |
| A12 | `bin` добавляется в `PATH` только на словах (в README) | После установки команды не находятся. |
| A13 | Нет `upgrade`, `search`, `info`; `list` показывает доступные пакеты, а не установленные | Непривычная семантика команд. |

## 3. Архитектура в одном абзаце

Автор репозитория пакетов пишет **манифесты** (`packages/<name>.json`). Генератор **`flan-build`** проверяет их, скачивает каждый архив один раз, считает хэши, убеждается, что нужные файлы в архиве есть, и собирает **один подписанный сжатый индекс** `index.flan`. Клиент **`flan`** скачивает индекс (условным запросом — обычно 0 байт), проверяет подпись, а при установке делает **ровно один** сетевой запрос — за самим архивом, — сверяет SHA-256 на лету, распаковывает своим кодом в версионный каталог и создаёт маленькую `.exe`-прослойку.

```
 flan-packages (git)                    машина пользователя
 ┌──────────────────────┐               ┌──────────────────────────────┐
 │ packages/*.json      │               │ flan sync                    │
 │        │             │   HTTPS       │   If-None-Match → 304 / 200  │
 │   flan-build         │──index.flan──▶│   проверка подписи           │
 │   (проверка, хэши,   │               │   защита от отката           │
 │    подпись)          │               │                              │
 │        ▼             │               │ flan install rg              │
 │ index.flan           │               │   поиск в индексе (локально) │
 └──────────────────────┘               │   скачивание архива + SHA-256│
                                        │   распаковка → apps\…\ver\   │
 upstream (GitHub Releases) ──архив────▶│   прослойка bin\rg.exe       │
                                        │   квитанция apps\…\receipt   │
                                        └──────────────────────────────┘
```

Ключевые решения:

- **Один индекс = единственный источник правды** для клиента. Нет `meta/`, нет числовых id. Ключ — имя пакета.
- **Клиент не разбирает JSON.** JSON нужен только людям (манифесты) и генератору.
- **Доверие идёт от ключа подписи**, а не от GitHub. HTTPS — транспорт, не гарантия.

## 4. Компоненты и раскладка исходников

```
flan/
├── flan.sln
├── src/
│   ├── cli/          main.cpp — разбор аргументов, вывод, коды возврата
│   ├── core/         index.cpp, install.cpp, receipt.cpp, shim.cpp, lock.cpp
│   ├── net/          http.cpp (WinHTTP)
│   ├── io/           fs.cpp (только W-функции), zip.cpp, console.cpp
│   └── crypto/       sha256.cpp (потоковый), signature.cpp (ECDSA P-256)
├── include/flan/     format.hpp, validate.hpp, keys.hpp, … (общие с flan-build)
├── shim/             shim.cpp — отдельный проект, без CRT, ~5–10 КБ
├── tools/flan-build/ генератор индекса (C++, может тянуть nlohmann — размер неважен)
├── third_party/      tinfl.c (inflate из miniz, public domain/MIT); nlohmann/json.hpp — только для flan-build
└── tests/
```

`format.hpp`, `validate.hpp` и `zip.cpp` **общие** для клиента и генератора: генератор отвергает всё, что отверг бы клиент, по одному и тому же коду.

Эта раскладка вводится первым шагом этапа 1 — только переносами, без изменения логики.

## 5. Репозиторий пакетов

### 5.1. Раскладка

```
flan-packages/
├── packages/
│   ├── ripgrep.json
│   └── …
├── index.flan        ← генерируется flan-build, руками не править
└── README.md
```

`core.flan` и `meta/` удаляются. Пока пакеты добавляет только автор, `index.flan` коммитится в `main` рядом с манифестами. Когда появятся чужие PR и CI, индекс уедет в отдельную ветку `dist` или в GitHub Releases (см. [13](#13-открытые-вопросы)).

URL индекса в клиенте: `https://raw.githubusercontent.com/muirbil/flan-packages/main/index.flan`. Для отладки и для проверки до публикации переопределяется переменной `FLAN_REPO` (вводится на этапе 1). Это база, к которой дописывается `/index.flan`:

- начинается с `https://` — база URL;
- иначе — путь к локальному каталогу (например, к клону `flan-packages`), и файл копируется вместо скачивания. Скопированный файл проходит **те же шаги приёма**, что и скачанный ([§6.1](#61-конверт-то-что-лежит-на-сервере)): копия во временный `.part`, полная проверка, атомарная замена `state\index.flan`. Прямо в `state\index.flan` он не кладётся никогда.

Подпись при этом всё равно проверяется (с этапа 4).

### 5.2. Манифест

```json
{
  "name": "ripgrep",
  "version": "14.1.1",
  "description": "Recursively search directories for a regex pattern",
  "homepage": "https://github.com/BurntSushi/ripgrep",
  "license": "MIT",
  "bin": ["rg.exe"],
  "arch": {
    "x64": {
      "url": "https://github.com/BurntSushi/ripgrep/releases/download/{version}/ripgrep-{version}-x86_64-pc-windows-msvc.zip",
      "extract_dir": "ripgrep-{version}-x86_64-pc-windows-msvc",
      "sha256": "<заполняет flan-build hash>"
    },
    "x86": {
      "url": "https://github.com/BurntSushi/ripgrep/releases/download/{version}/ripgrep-{version}-i686-pc-windows-msvc.zip",
      "extract_dir": "ripgrep-{version}-i686-pc-windows-msvc",
      "sha256": "<заполняет flan-build hash>"
    }
  }
}
```

| Поле | Обязательное | Правило |
|---|---|---|
| `name` | да | `isSafeName`, только строчные буквы, совпадает с именем файла. Имя из командной строки клиент приводит к нижнему регистру |
| `version` | да | `isSafeName` (становится именем каталога). Строже прежнего `isSafeVersion`: `1.0+build` не пройдёт |
| `description` | нет | ≤ 100 байт, без управляющих символов |
| `homepage`, `license` | нет | только для людей, в индекс не попадают |
| `bin` | да | 1–8 элементов, каждый проходит `normalizeRelativePath` и оканчивается на `.exe` (прослойка запускает цель через `CreateProcessW`, а он не запускает `.cmd`/`.bat`); путь относительно корня приложения (после `extract_dir`). Имена команд (последний сегмент без `.exe`) внутри пакета не повторяются |
| `arch.<a>.url` | да | `https://`, без «плавающих» ссылок вроде `/latest/` — иначе хэш однажды перестанет совпадать |
| `arch.<a>.extract_dir` | нет | подкаталог архива, который становится корнем приложения; проходит `normalizeRelativePath` |
| `arch.<a>.sha256` | да | 64 hex-символа |
| `arch.<a>.kind` | нет | `zip` (по умолчанию) или `exe` — одиночный файл, копируется как есть. Для `exe` ещё не определено, под каким именем ложится файл и что тогда значит `bin`, поэтому до этапа 4 (самообновление, где это понадобится) генератор `kind = exe` отвергает |

- Неизвестные поля — и на верхнем уровне, и внутри `arch.<a>` — ошибка: почти всегда это опечатка вроде `extractdir`, которая иначе молча потерялась бы.
- Ключи `arch`: `x64`, `x86` и `arm64`. Последний формат резервирует; клиент его пока не выбирает (см. [7.6](#76-транзакция-установки--обновления), шаг 1).

`{version}` подставляется генератором. Обновление пакета = поменять `version` + `flan-build hash`. Больше ничего руками.

### 5.3. Правила приёма пакетов

- Только портативные сборки от первоисточника (предпочтительно GitHub Releases апстрима). flan ссылается на апстрим, а не хранит копии.
- Ссылка указывает на конкретную версию, а не на «последнюю».
- Архив ≤ 512 МБ, распакованный размер ≤ 2 ГБ. Распакованный размер генератор проверяет с этапа 3, своим `zip.cpp`: `tar.exe -tf` размеров не сообщает.
- Имя пакета — имя апстрима в нижнем регистре.

## 6. Формат индекса (`index.flan`, формат 2)

Все числа little-endian, структуры упакованы (`#pragma pack(1)`), размеры зафиксированы `static_assert`. Файл состоит из **конверта** и **тела**.

### 6.1. Конверт (то, что лежит на сервере)

```cpp
struct Envelope {               // 88 байт
    char     magic[8];          // "FLANIDX\0"
    uint16_t envelope_version;  // = 1
    uint8_t  key_id;            // какой встроенный публичный ключ проверяет подпись; 0 = без подписи
    uint8_t  compression;       // 0 = нет, 1 = raw deflate
    uint32_t payload_size;      // байт тела после конверта (сжатого)
    uint32_t raw_size;          // байт тела после распаковки
    uint32_t reserved;          // = 0
    uint8_t  signature[64];     // ECDSA P-256, r||s
};
// Подпись покрывает SHA-256( первые 24 байта конверта || payload ).
```

- **`key_id = 0` — индекс без подписи**, `signature` — нули. Такие индексы выпускает только генератор этапов 1–3. Клиент этапа 4 и новее отвергает `key_id = 0` **безусловно** — без флагов и переменных окружения, иначе атака «снять подпись» становится тривиальной.
- **`compression = 0` → `payload_size == raw_size`**, иначе индекс отвергается.

Порядок проверки в клиенте — **строго такой**:

1. Размер файла ≤ 8 МБ и `== sizeof(Envelope) + payload_size`.
2. `magic`, `envelope_version`, известный `key_id`, `reserved == 0`.
3. **Подпись** (с этапа 4; до него `key_id = 0` и шаг пропускается). До её проверки ни один байт тела не попадает в распаковщик или парсер.
4. Распаковка с жёстким потолком `raw_size ≤ 32 МБ`; результат обязан быть ровно `raw_size` байт (с этапа 2; до него `compression = 0`).
5. Разбор тела с проверкой всех границ (как в прежнем `loadDatabase`, только в 64-битной арифметике везде).
6. `generated_at` ≥ значения из последнего принятого индекса — иначе отказ («похоже на откат индекса») (с этапа 4).
7. Атомарная замена локального `index.flan` (запись в `.part` → `MoveFileExW(…, MOVEFILE_REPLACE_EXISTING)`).

### 6.2. Тело

```cpp
struct IndexHeader {            // 32 байта
    char     magic[8];          // "FLANBODY"
    uint16_t format;            // = 2
    uint16_t entry_size;        // = sizeof(IndexEntry); позволяет добавлять поля в конец
    uint32_t entry_count;
    uint64_t generated_at;      // unix-время сборки; монотонно растёт
    uint32_t strings_offset;    // от начала тела
    uint32_t strings_size;
};

struct StrRef { uint32_t off; uint32_t len; };   // off — от начала пула строк (strings_offset); без '\0'

struct IndexEntry {             // 88 байт
    StrRef   name;
    StrRef   version;
    StrRef   url;
    StrRef   extract_dir;       // len = 0 → корень архива
    StrRef   bins;              // "rg.exe" или "bin\\a.exe;bin\\b.exe" (';' недопустим в путях — разделитель однозначен)
    StrRef   description;
    uint32_t archive_size;      // точный размер архива в байтах
    uint8_t  arch;              // 1 = x86, 2 = x64, 3 = arm64
    uint8_t  kind;              // 1 = zip, 2 = exe
    uint16_t reserved;
    uint8_t  sha256[32];        // бинарный, не hex
};
```

- Таблица записей начинается сразу за `IndexHeader` (смещение 32 от начала тела), а `strings_offset` не меньше её конца.
- Записи **отсортированы по `(name, arch)`**: имена сравниваются побайтово, при равных именах — по числовому `arch`.
- Пределы, которые клиент проверяет сверх границ: `entry_size` ≤ 4096; длина любой строки ≤ 4096 байт; `archive_size` от 1 байта до 512 МБ; `arch` ∈ {1, 2, 3}; `kind` ∈ {1, 2}. Поле `reserved` записи не проверяется — его могут занять будущие версии.
- `entry_size` больше известного клиенту `sizeof(IndexEntry)` → клиент читает известную часть каждой записи и пропускает остаток; меньше → индекс отвергается.
- **Когда что проверяется.** При приёме индекса (`sync`) клиент один раз проверяет **все** записи: каждую строку — той же проверкой, что и генератор (`isSafeName`, `normalizeRelativePath`, `isHttpsUrl`…), и порядок сортировки. Индекс подписан, но двойная проверка дешёвая и защищает от ошибки в самом генераторе. Остальные команды работают с уже принятым локальным индексом: границы проверяются всегда, строки — только у найденной записи, поиск двоичный.
- `archive_size` даёт: прогресс без `Content-Length`, проверку свободного места до загрузки, сообщение «будет скачано 4.2 МБ» перед установкой, раннюю остановку при превышении.
- Отдельный «хэш версии» (`hash_v`) больше не нужен: **идентичность сборки — её `sha256`**. Обновление доступно, если `sha256` в индексе ≠ `sha256` в квитанции. Сравнивать строки версий (`1.10` vs `1.9`, `-beta`) не нужно вовсе; репозиторий — источник правды, в том числе при откате версии пакета автором.

**Оценка размера:** ~88 байт записи + ~230 байт строк; после deflate (URL-ы хорошо сжимаются) ≈ 100–130 байт на пакет. 1000 пакетов ≈ 120 КБ — это ~15 с на 64 кбит/с, и только когда индекс действительно изменился.

### 6.3. Подпись и ключи

- Алгоритм — **ECDSA P-256 + SHA-256 через CNG (`BCryptVerifySignature`)**. Он есть в Windows начиная с Vista, поэтому проверка подписи добавляет к `flan.exe` десятки строк кода и ноль байт сторонних библиотек. Ed25519 в CNG нет — его пришлось бы встраивать (например, Monocypher).
- Публичные ключи вкомпилированы в `include/flan/keys.hpp` (до 2 штук: текущий и следующий — для ротации без поломки старых клиентов). `key_id` в конверте выбирает ключ.
- Приватный ключ лежит **вне** репозитория у автора (желательно зашифрован через DPAPI). `flan-build keygen` создаёт пару и печатает публичный ключ как C-массив.
- Компрометация ключа = выпуск новой версии `flan` с новым ключом. Это осознанная цена простоты (без TUF-иерархии).

## 7. Клиент

### 7.1. Каталоги

Корень — `%FLAN_HOME%`, по умолчанию `%USERPROFILE%\.flan` (получаем через `SHGetKnownFolderPath(FOLDERID_Profile)` — Unicode). Переменная `FLAN_HOME` позволяет держать всё, например, на флешке. За пределы этой папки flan пишет только в одно место — `HKCU\Environment\Path` (см. [7.8](#78-path)); поэтому права администратора не нужны.

```
%FLAN_HOME%\
├── bin\                    ← единственное, что добавляется в PATH
│   ├── flan.exe            ← сам клиент (не прослойка)
│   ├── .shim.exe           ← эталонная прослойка, извлекается из ресурсов flan.exe
│   ├── rg.exe              ← жёсткая ссылка на .shim.exe (или копия, если не NTFS)
│   └── rg.shim             ← куда вести
├── apps\
│   └── ripgrep\
│       ├── 14.1.1\         ← содержимое архива (после extract_dir)
│       └── receipt         ← квитанция установки
├── cache\
│   └── <sha256>            ← скачанные архивы, адресуются содержимым
├── state\
│   ├── index.flan          ← последний принятый индекс
│   └── index.state         ← etag, generated_at
├── tmp\
└── lock
```

Все пути внутри — `std::wstring`, все вызовы ФС — W-функции с префиксом `\\?\` (снимает ограничение `MAX_PATH`). UTF-8 используется только на границах: вывод, файлы состояния, строки из индекса.

### 7.2. Сеть

Расширяем текущий `downloadFile`:

- **TLS:** явно `WINHTTP_OPTION_SECURE_PROTOCOLS = TLS1_2 | TLS1_3`. На Windows 7 WinHTTP по умолчанию TLS 1.2 не включает, а GitHub без него не работает.
- **Прокси:** `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY` (Windows 8.1+), с откатом на `DEFAULT_PROXY`.
- **Таймауты:** соединение 15 с, приём 60 с между пакетами данных — на медленном канале медленно не значит мёртво.
- **Редиректы:** разрешены (GitHub Releases перекидывает на `objects.githubusercontent.com`), но только HTTPS → HTTPS (`WINHTTP_OPTION_REDIRECT_POLICY`).
- **Условный запрос индекса:** `If-None-Match: <etag>`. Ответ `304` → «индекс актуален», 0 байт тела.
- **Докачка архивов:** если в `cache\<sha256>.part` уже что-то есть и сервер отвечает `Accept-Ranges: bytes` — запрос `Range: bytes=N-`. Ответ `206` → дописываем; `200` → начинаем заново. Докачка безопасна, потому что в конце всё равно сверяется SHA-256.
- **Повторы:** до 3 попыток с паузой 2/5/10 с для сетевых ошибок и 5xx; 4xx — сразу ошибка.
- **Хэш на лету:** SHA-256 обновляется прямо в цикле чтения. При докачке существующая часть хэшируется один раз перед продолжением. Второго прохода по файлу нет.
- **Лимиты:** `archive_size` из индекса известен заранее; больше этого размера не принимаем ни байта.
- **Прогресс:** только если stdout — консоль (`GetConsoleMode`); при перенаправлении — одна строка в конце. Символы ASCII (`[#####-----]`), чтобы не ломаться на старых консольных шрифтах.

### 7.3. Распаковка

Своя, в процессе, на базе `tinfl` (inflate из miniz, ~25 КБ исходников). Поддерживаем zip: stored + deflate, ZIP64 — нет (архивы ≤ 512 МБ).

Каждое имя в архиве проверяется **до записи**. Здесь не белый список (в архивах бывают пробелы, скобки, `+`), а запреты:

- нет `..`-сегментов, абсолютных путей, букв дисков, `:` (альтернативные потоки NTFS);
- нет управляющих символов, точек и пробелов в конце сегмента, зарезервированных имён (`CON`, `NUL`, …);
- симлинки и записи-устройства отвергаются;
- суммарный распакованный размер ≤ 2 ГБ, коэффициент сжатия отдельной записи ≤ 1000 (защита от zip-бомб);
- CRC32 каждой записи проверяется.

`extract_dir` применяется при распаковке: записи вне него пропускаются, префикс срезается.

Почему не `tar.exe`: его нет на старых системах, он стартует отдельный процесс (заметно на Celeron + антивирус) и не позволяет проверить имена заранее; префикс он срезать умеет, но вслепую. А `tinfl` всё равно нужен для сжатого индекса. До этапа 3 распаковка остаётся на `tar.exe`, а `extract_dir` применяется так: архив целиком распаковывается в staging, и корнем приложения становится `staging\<extract_dir>` (см. [7.6](#76-транзакция-установки--обновления)).

### 7.4. Прослойки (`shim`)

Отдельный крошечный `shim.exe` без CRT (только `kernel32`), вшитый в `flan.exe` как ресурс. В `bin\` лежит один эталон, а `rg.exe`, `fd.exe` и т.д. — жёсткие ссылки на него (на не-NTFS — копии).

`rg.shim` — текст UTF-8:

```
target=..\apps\ripgrep\14.1.1\rg.exe
package=ripgrep
```

Путь относительный к `bin\` — перенос `FLAN_HOME` ничего не ломает.

Поведение `shim.exe`:

1. Берёт собственное имя (`GetModuleFileNameW`), читает соседний `.shim`.
2. `CreateProcessW(target, <хвост GetCommandLineW() после argv[0]>)` — аргументы передаются **байт в байт**, без повторного разбора.
3. Наследует консоль и дескрипторы; создаёт Job Object с `KILL_ON_JOB_CLOSE` (убили прослойку — умер и ребёнок).
4. Игнорирует Ctrl+C у себя (`SetConsoleCtrlHandler(NULL, TRUE)`) — сигнал обрабатывает только сама программа.
5. Ждёт завершения и возвращает **тот же код выхода**.

`package=` нужен для конфликтов: если `bin\python.exe` уже принадлежит другому пакету, установка отказывает с понятной ошибкой.

Известное ограничение: прослойка — консольное приложение, поэтому GUI-программа, запущенная через неё из Проводника, мигнёт консольным окном. В v1 ориентируемся на консольные утилиты (см. [13](#13-открытые-вопросы)).

### 7.5. Квитанция (`apps\<name>\receipt`)

Простой `key=value` в UTF-8, без JSON:

```
name=ripgrep
version=14.1.1
dir=14.1.1
arch=x64
sha256=<64 hex-символа — тот же, что в индексе>
bins=rg.exe
installed_at=2026-11-17T15:00:00Z
```

- **`dir`** — фактическое имя каталога версии внутри `apps\<name>\`. Оно может отличаться от `version` (см. [7.6](#76-транзакция-установки--обновления), шаг 6). `uninstall`, повторный `install` и удаление старой версии берут путь **только** из `dir` и никогда не собирают его из `version`.
- **`bins`** — через `;`, как в индексе.
- При чтении каждое значение проходит ту же проверку, что и при записи (`name`, `version`, `dir` — `isSafeName`; каждый элемент `bins` — `normalizeRelativePath`). Квитанция, где хоть одно значение не прошло проверку, считается повреждённой, и flan не берёт из неё пути.

Своя квитанция у каждого пакета — вместо общего `installed.json`. Установленные пакеты = обход `apps\*\receipt`. Повреждение одной квитанции не трогает остальные; запись атомарная (`receipt.tmp` → `MoveFileExW`).

### 7.6. Транзакция установки / обновления

Команды, меняющие состояние (`sync`, `install`, `uninstall`, позже `upgrade`, `cleanup`, `setup`), работают под файловой блокировкой `%FLAN_HOME%\lock`:

- Файл `lock` лежит постоянно. Блокировка — это его открытие через `CreateFileW` с нулевым share mode на всё время команды. Снимается закрытием дескриптора, в том числе когда процесс упал или убит: дескрипторы закрывает система.
- `ERROR_SHARING_VIOLATION` — блокировку держит другой `flan`: ждать до 10 с, потом выйти с кодом 6.
- `ERROR_ACCESS_DENIED` и любая другая ошибка — сразу понятное сообщение и код 1. Ждать бессмысленно: это права или атрибут «только чтение» на файле либо папке.
- `FILE_FLAG_DELETE_ON_CLOSE` не используется. С ним, пока система удаляет только что закрытый файл, второй процесс получает `ERROR_ACCESS_DENIED`, и «занято» становится неотличимо от настоящей ошибки прав.

Читающие команды (`list`, `installed`, позже `search`, `info`) работают без блокировки. Это безопасно, потому что всё, что они читают, — `state\index.flan` и квитанции — записывается атомарно: во временный файл, затем `MoveFileExW`. Читатель видит либо старую версию файла, либо новую, но никогда не половину. Худшее, что может случиться, — список на мгновение устареет относительно параллельной установки.

1. Найти запись в локальном индексе для архитектуры **ОС** (`GetNativeSystemInfo`), а не разрядности самого flan: на x64 — x64, если её нет, то x86; на x86 — только x86; на ARM64 — понятная ошибка «архитектура не поддерживается», без отката на x64/x86 (ARM64 пока только зарезервирован, см. §1).

   Оговорка про ARM64. Из x86- и x64-процесса `GetNativeSystemInfo` на ARM64 возвращает не ARM64, а эмулируемую архитектуру: x64, если система эмулирует x64 (Windows 11), иначе x86. Так что обещанная ошибка для ARM64 у наших сборок не сработает никогда, и flan поставит x64- или x86-пакет. Это безвредно: такой пакет на этой системе работает под той же эмуляцией, что и сам flan. Надёжно узнать архитектуру хоста можно через `IsWow64Process2` (параметр `pNativeMachine`). Она появилась в Windows 10 1709, поэтому её придётся загружать через `GetProcAddress`, чтобы не сломать 7 / 8.1. Понадобится, когда дойдём до ARM64.
2. Если квитанция есть и `sha256` совпадает — «уже установлено», выход. Если квитанция есть, а `sha256` другой, — это обновление: дальше те же шаги, а старая версия — каталог из `dir` её квитанции.
3. Есть `cache\<sha256>` и он цел → пропустить загрузку. Иначе — скачать в `cache\<sha256>.part` (с докачкой), сверить размер и SHA-256, переименовать. (С этапа 2. На этапе 1 кэша нет: архив качается в `tmp\` и удаляется после установки.)
4. Распаковать в `apps\<name>\.staging-<pid>\`. Корень приложения — `staging\<extract_dir>` (или сам staging, если `extract_dir` пуст).
5. Проверить, что все `bins` существуют и являются файлами.
6. Переименовать корень приложения → `apps\<name>\<dir>\`, где `dir = version`. Если такой каталог уже есть:
   - на него не указывает квитанция — это остаток прерванной установки, он удаляется, и `dir = version` (если удалить не удалось — как в следующем случае);
   - на него указывает квитанция (та же версия пересобрана с другим `sha256` или сменилась архитектура) — `dir = <version>-<первые 8 hex-символов sha256>`. Если занят и этот каталог — установка отказывает с понятной ошибкой.

   Остаток staging удаляется.
7. Записать прослойки (`.shim` атомарно, жёсткую ссылку — если её ещё нет; на этапах 1–2 — `.bat`, см. [12](#12-план-перехода)).
8. Записать квитанцию с фактическим `dir`. **Это точка фиксации**: до неё установка считается несостоявшейся.
9. Удалить каталог старой версии (путь — из `dir` старой квитанции). Если файл в нём занят (программа запущена) — оставить, записать в `state\pending-delete` и повторить при следующем запуске `flan`.

Сбой на шагах 3–7 → удаляется только staging; старая версия и её прослойки продолжают работать.

**Почему версионные каталоги, а не один фиксированный `apps\ripgrep\`:** каталог с запущенным `.exe` нельзя ни переименовать, ни очистить. Версионный каталог позволяет обновлять программу, пока она работает. «Стабильный путь» для пользователя — это `bin\rg.exe`, а не путь внутри `apps\`.

Для программ, хранящих настройки рядом с собой, позже появится поле `persist` (что переносить из старой версии в новую). В v1 его нет.

### 7.7. Команды

| Команда | Что делает |
|---|---|
| `flan sync` | Обновить индекс (условный запрос). |
| `flan search [текст]` | Поиск по имени и описанию; без аргумента — все пакеты. |
| `flan info <pkg>` | Версия, описание, размер загрузки, установлен ли. |
| `flan install <pkg>…` | Установить. Если пакет уже установлен, но `sha256` в индексе другой, — обновить (транзакция [7.6](#76-транзакция-установки--обновления)). Если индекса нет — сначала `sync`. Если индекс старше 7 дней — предупреждение. |
| `flan uninstall <pkg>…` | Удалить каталог, прослойки, квитанцию. |
| `flan upgrade [pkg…]` | Обновить указанные или все, у которых `sha256` в индексе отличается. |
| `flan list` | Установленные пакеты. **Меняет текущую семантику** — на этапе 5, вместе с появлением `search`, чтобы ни на одном этапе не пропадал способ увидеть доступные пакеты. До этого `list` показывает доступные (из индекса), а установленные — `flan installed`. |
| `flan cleanup` | Очистить `cache\` и неудалённые старые версии. |
| `flan setup` | Добавить `bin\` в PATH пользователя, скопировать себя в `bin\`. `--remove` — обратное. |

Флаги: `--no-progress`, `--help`. Больше пока не нужно.

Коды возврата: `0` — успех, `1` — прочая ошибка, `2` — неверные аргументы, `3` — сеть, `4` — целостность (хэш, подпись, откат индекса), `5` — пакет не найден, `6` — занята блокировка. Вводятся на этапе 1 для всех переписанных команд.

### 7.8. PATH

`flan setup` правит `HKCU\Environment\Path` напрямую:

- читает значение **без раскрытия** переменных и сохраняет исходный тип (`REG_EXPAND_SZ` / `REG_SZ`);
- добавляет `%USERPROFILE%\.flan\bin` (или фактический `FLAN_HOME`), только если его там ещё нет;
- рассылает `WM_SETTINGCHANGE` с `"Environment"` через `SendMessageTimeoutW`.

`setx` не используется: он обрезает значение до 1024 символов и раскрывает переменные.

### 7.9. Самообновление

`flan` — обычный пакет в индексе (`kind = exe`). `flan upgrade flan`:

1. скачивает и проверяет новый `flan.exe` как любой пакет;
2. переименовывает работающий `bin\flan.exe` → `bin\flan.exe.old` (работающий `.exe` переименовать можно, перезаписать — нет);
3. кладёт новый на место;
4. при следующем запуске `flan.exe.old` удаляется.

### 7.10. Вывод и ошибки

- Без `<iostream>`. Свой маленький слой: `WriteConsoleW` для консоли, `WriteFile` с UTF-8 при перенаправлении.
- Ошибки — коды возврата функций (`enum class Error` + сообщение), не исключения. `/EHsc` остаётся только ради `std::bad_alloc`.
- Никаких `std::filesystem`: всё нужное есть в `io/fs.cpp` поверх W-функций.

## 8. `flan-build` (генератор)

Отдельный проект в том же решении, на C++, общий код с клиентом. Ему можно всё: `nlohmann/json`, `<iostream>`, `<filesystem>` — размер не важен.

| Команда | Что делает |
|---|---|
| `flan-build check packages\` | Проверка манифестов без сети: схема, имена, уникальность, `{version}` раскрывается. |
| `flan-build hash packages\ripgrep.json [--force]` | Скачивает архивы, вписывает `sha256`, проверяет `extract_dir` и `bin` внутри архива. |
| `flan-build index packages\ -o index.flan --key <путь>` | Полная проверка + сборка + сжатие + подпись. До этапа 4 `--key` нет, индекс собирается с `key_id = 0`; до этапа 2 — без сжатия. |
| `flan-build keygen` | Новая пара ключей. |

Для каждого архива генератор **реально** проверяет, что он открывается тем же `zip.cpp`, что и у клиента, что `extract_dir` существует, а каждый `bin` — файл. До этапа 3, пока своего `zip.cpp` нет, содержимое архива проверяется через `System32\tar.exe -tf` — тем же `tar.exe`, которым распаковывает клиент. Скачанные архивы кэшируются локально по `sha256` (в `.cache\`, не коммитится), поэтому повторная сборка индекса сеть не трогает.

**Когда `hash` вправе вписать хэш.** Генератор сверяется с предыдущим `index.flan` в корне репозитория пакетов, рядом с `packages\`:

- запись `(name, arch)` в предыдущем индексе с **тем же URL**, но хэш скачанного архива другой → **ошибка**: апстрим подменил файл под той же ссылкой;
- URL изменился (новая версия) или записи в предыдущем индексе нет → вписать новый хэш;
- `--force` — принять новый хэш и при том же URL, когда апстрим законно перезалил файл. В выводе — явное предупреждение со старым и новым хэшем.

`hash` идемпотентен: если ни один хэш не изменился, файл манифеста не перезаписывается вовсе. Если записать нужно, сохраняются переводы строк и BOM исходного файла — иначе при `core.autocrlf` каждый запуск менял бы рабочую копию. Форматирование при первой записи выравнивается (отступ 2 пробела, массивы — по элементу на строку); порядок полей и шаблоны `{version}` остаются как у автора.

`generated_at` = текущее время, но не меньше, чем в предыдущем `index.flan` + 1.

## 9. Модель угроз

| Угроза | Защита |
|---|---|
| Подмена индекса (взлом репозитория, токена, MITM) | Подпись ECDSA; ключ не на GitHub. |
| Подсовывание старого подписанного индекса с уязвимой версией | `generated_at` не может уменьшаться. |
| Подмена архива у апстрима или в пути | SHA-256 из подписанного индекса, проверка до распаковки. |
| Обход каталога через имена (`..\`, `C:\`, `CON`, ADS) | Белый список для имён пакетов и `bin`; запреты для имён внутри архивов; всё в одном `validate.hpp`. |
| Zip-бомба, бесконечный поток | Лимиты размеров на загрузку, распаковку, коэффициент сжатия. |
| Подмена `tar.exe` / поиск в текущем каталоге | Внешних процессов при установке нет совсем. |
| Порча состояния при сбое или параллельном запуске | Блокировка, атомарные переименования, квитанции по пакетам. |
| Выполнение кода пакета при установке | Не поддерживается в принципе: нет скриптов, нет установщиков. |
| Перехват команды чужим пакетом (`bin\python.exe`) | Владелец прослойки записан в `.shim`; конфликт = отказ. |

Вне модели: вредоносная программа, которую апстрим сам опубликовал под своей подписью; компрометация машины автора вместе с приватным ключом.

## 10. Сборка и размер

Release:

- `/O1` (минимум размера: на Celeron узкое место — диск и сеть, а не процессор), `/GL`, `/Gy`, `/LTCG`, `/OPT:REF`, `/OPT:ICF`
- `/MT` — статический CRT, без VC++ Redistributable
- `/GS`, `/DYNAMICBASE`, `/NXCOMPAT`, `/HIGHENTROPYVA` — оставляем, они почти ничего не весят
- `/permissive-`, `/std:c++17`

Бюджет размера x64 Release:

| Состояние | Размер |
|---|---|
| Сейчас (с `nlohmann`, `iostream`, `filesystem`) | ~430 КБ |
| Цель v1 | ≤ 200 КБ |
| Желательно | ≤ 150 КБ |
| `shim.exe` | ≤ 10 КБ |

Размер измеряется после каждой сборки; рост больше чем на 10 КБ без причины — повод разобраться.

## 11. Тестирование

- **Модульные:** `validate.hpp` (таблица хороших и плохих имён), разбор индекса, `zip.cpp`, разбор `.shim` и квитанций.
- **Вредоносные входы:** набор zip-файлов (`..\`, абсолютные пути, ADS, симлинки, бомба, битый CRC, обрезанный архив) и индексов (обрезанный, с неверными смещениями, с неверной подписью, со старым `generated_at`). Всё должно отвергаться с понятной ошибкой, без падения.
- **Фаззинг:** `/fsanitize=fuzzer` (MSVC) для разбора индекса и zip.
- **Сквозной:** тестовый ключ + локальный каталог `FLAN_REPO` с индексом; сценарий `sync → install → upgrade → uninstall`, плюс обрыв загрузки посередине и докачка.
- **Ручной чек-лист перед релизом:** кириллическое имя пользователя, путь длиннее 260 символов, FAT32-флешка как `FLAN_HOME`, 32-битная Windows, запущенная программа во время `upgrade`.

## 12. План перехода

Каждый этап заканчивается работающим `flan install ripgrep` от начала до конца.

**Этап 0 — зафиксировать текущее.**
`git pull` (локальная ветка отстаёт на коммит с README), закоммитить сделанные исправления как есть. Это точка отката.

**Этап 1 — один источник правды.**
- Раскладка исходников по [§4](#4-компоненты-и-раскладка-исходников) — первым шагом, только переносы.
- `flan-build`: `check`, `hash` (с правилами и `--force` из [§8](#8-flan-build-генератор)), `index` без подписи и сжатия. Содержимое архивов проверяется через `tar.exe -tf`.
- Формат индекса 2: `compression = 0`, `key_id = 0`, подпись нулевая и не проверяется.
- `FLAN_REPO` ([§5.1](#51-раскладка)): проверка до публикации — на локальном клоне `flan-packages`.
- Версионные каталоги, квитанции с `dir=`, транзакция [§7.6](#76-транзакция-установки--обновления) без кэша, блокировка, коды возврата.
- `.bat`-прослойки пока остаются. Вторая строка (после `@echo off`) — `rem package=<name>`: установка отказывает, если `.bat` с тем же именем принадлежит другому пакету, а `uninstall` не трогает чужие.
- Команды: `list` — доступные пакеты, `installed` — установленные (смена семантики `list` — на этапе 5).
- В `flan-packages`: `packages/ripgrep.json` с настоящим SHA-256, удалить `core.flan` и `meta/`.
- PATH: `flan setup` появится только на этапе 3, поэтому на этапе 1 `%USERPROFILE%\.flan\bin` добавляется в PATH пользователя вручную, через окно «Переменные среды» (`rundll32 sysdm.cpl,EditEnvironmentVariables`). Не через `setx` — он обрезает значение и раскрывает переменные ([§7.8](#78-path)).

*Готово, когда:* на чистом `%USERPROFILE%\.flan` работают `flan sync`, `flan install ripgrep` и `rg --version` с настоящим SHA-256 в манифесте. Сначала проверяется через `FLAN_REPO` на локальный клон, затем — против GitHub после публикации `flan-packages`.

**Этап 2 — медленный интернет.**
`tinfl`, сжатый индекс, `If-None-Match`, докачка, хэш на лету, кэш по `sha256`, `archive_size`.
*Готово, когда:* повторный `sync` передаёт 0 байт тела; обрыв на 50% архива и повторный `install` докачивают только остаток.

**Этап 3 — без лишнего веса.**
Своя распаковка вместо `tar.exe`, Unicode-пути, `shim.exe`, удаление `nlohmann`, `iostream`, `filesystem` из клиента. `flan setup`.
*Готово, когда:* x64 Release ≤ 200 КБ; всё работает под пользователем с кириллическим именем.

**Этап 4 — доверие.**
Подпись, ключи, защита от отката, самообновление.
*Готово, когда:* изменённый вручную байт в `index.flan` даёт код возврата 4.

**Этап 5 — рост репозитория.**
`upgrade`, `search`, `info`, `cleanup`; 20–30 популярных консольных утилит (fd, bat, jq, fzf, 7zip, …); CI, который запускает `flan-build check` на PR.

## 13. Открытые вопросы

1. **Минимальная Windows.** Предложение: официально 10+, 7/8.1 «не ломаем намеренно». Или явно отказаться от 7?
2. **Подпись:** ECDSA P-256 через CNG (0 байт зависимостей) — или Ed25519 через встроенный Monocypher (меньше подпись, но +код)? Предложение: P-256.
3. **Где публиковать индекс,** когда появится CI: ветка `dist`, GitHub Releases или по-прежнему `main`?
4. **GUI-программы:** поддерживать (тогда прослойке нужен GUI-вариант без консоли) или явно оставить за рамками v1?
5. **Оставить `.bat`-прослойки как запасной вариант,** если антивирус пометит `shim.exe` (такое бывало у похожих прослоек)?
6. **`depends`:** резервировать поле в формате сейчас (`entry_size` и так позволяет расширение) или не трогать до реальной необходимости?
